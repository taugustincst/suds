# SUDS — notes for contributors and AI assistants

* Zero runtime dependencies: Node 22 built-ins only (`node:sqlite`, `node:crypto`, `node:http`). Do not add npm packages without a strong reason; the small supply chain is a security feature.
* Backend: `server/` — `app.js` (request pipeline and the one list of route modules), `auth.js` (sessions, RBAC matrix, caseload scoping), `crud.js` (generic client-scoped CRUD), `routes/*`, `importers/*`, `schema.sql`.
* All PHI columns end in `_enc` (AES-256-GCM via `server/crypto.js`); searchable copies end in `_idx` (HMAC blind index). Never write PHI into plaintext columns, audit details, or logs. A new `_enc` column is picked up automatically by key rotation and by the sync consistency test — but it must also be declared in `server/sync-tables.js`, or `test/sync.test.js` fails.
* `server/schema.sql` is the only source of schema truth. `server/schema-text.js` (browser) and the version stamp in `public/sw.js` are generated by `scripts/gen-schema-text.js`, which `npm run build:local` runs; CI fails if either drifts. The native apps (`mobile/`) and desktop launchers (`launchers/`) were removed in 1.9.3 and live only in git history (`docs/PLATFORM.md`) — the web app is the only client (served by an office server, or published as SUDS on this device); do not bring them back or add native build steps.
* Two production ways to run SUDS (`docs/PLATFORM.md`): the office server (system of record for its programme; **Sign up** = an access request an administrator approves, `POST /api/auth/signup`, `users.access_status`) and the GitHub Pages build, **SUDS on this device** (`scripts/build-static-site.js`; records only in that browser; Sign up creates device accounts via `/api/local/signup`; device backups in `local/backup.js`). It is not a demo: never reintroduce demo/evaluation wording or a banner. `window.SUDS_STATIC_HOST` is an internal marker for behaviour differences only (no office sync, device sign-ups, storage confirmation, backup reminder).
* Schema changes need a migration in `server/db.js` as well as the change to `schema.sql` — `test/migrations.test.js` upgrades a real 1.6.1 database from `test/fixtures/schema-v4.sql` and asserts a fresh install and an upgraded one end up structurally identical.
* Anything that leaves the programme (a referral that names a client, an identified export) must go through `server/disclosure.js`, which checks the consent and writes the accounting record.
* Password hashing in a request path uses `hashPasswordAsync`/`verifyPasswordAsync`; the sync versions are for CLI scripts only, because scrypt blocks the event loop for ~90ms.
* Every PHI read/write must call `audit.log`. The audit table is hash-chained — never UPDATE or DELETE rows except via the retention purge.
* Frontend: `public/` vanilla ES modules, no build step. `app.js` has the DOM/form helpers; views register with `route()` and are imported in `main.js`. CSP forbids inline scripts.
* Tests: `npm test` (node:test). Add an API test for every new permission or route. Run the browser suite (`scripts/ui/run-all.sh`) after UI changes — its scripts must assert with the `ok()`/`eq()` helpers in `scripts/ui/assert.mjs`, not `console.log` values nobody compares.
* Dev data: `npm run seed` (fictional clients). Never seed production.
* Local mode is off by default on an office server (`LOCAL_MODE_ENABLED`, or the setup wizard's answer in `server.json`); `scripts/ui/run-all.sh` exports `LOCAL_MODE_ENABLED=true` for the suite's dev server. esbuild and sql.js are ignored by Dependabot and updated by hand with `npm run build:local` (docs/RELEASE.md).
* Local mode: `local/` holds the browser kernel (shims + sync runner). Rebuild `public/local/kernel.js` with `npm run build:local` after changing anything under `server/` and commit the result; test at `/?local=1`.
