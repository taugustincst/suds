# SUDS REST API

All endpoints are under `/api`. Authentication is a session cookie set by `POST /api/auth/login` (browser) or an `Authorization: Bearer <session token>` header; state-changing requests from a cookie session must include `X-Requested-With: suds`. Intake endpoints use an API key. Responses are JSON; errors are `{ error, fields? }`. List endpoints accept `limit`, `offset`, `client_id`, `from`, `to`, `mine=1` and `user_id` where applicable. Every PHI access is audited.

Permissions per role are defined in `server/auth.js` (`PERMS`). Generated by `scripts/gen-api-docs.js`.

## FHIR R4 API

`/fhir/R4` is a read-only FHIR R4 API for the county EHR or an HIE (Patient, EpisodeOfCare, Encounter, Consent, ServiceRequest, Task, Observation, DocumentReference, Organization, Location, HealthcareService, and Bulk Data `$export`). It answers in `application/fhir+json`, authenticates FHIR clients (created under Settings → FHIR clients, `/api/admin/fhir-clients`) with a 15-minute bearer token from `POST /fhir/R4/auth/token` (OAuth2 client credentials; the client signs a JWT with its registered key, SMART Backend Services `private_key_jwt`, or sends its secret; the secret is never itself a bearer token), and returns a client's records only under a live 42 CFR Part 2 consent naming the FHIR client's organisation, recording each disclosure. Endpoints, mappings, scopes and examples: [docs/integration/FHIR.md](integration/FHIR.md).

## Break-glass

Administrators may read a clinical note by sending `X-Break-Glass-Reason: <reason>` with `GET /api/notes/:id`; the access and reason are written to the audit log.

## Retries and concurrent edits

- **Idempotency-Key** (POST): send a key (1-255 printable characters) and a repeat of the same request by the same user within 24 hours returns the first answer (with `Idempotent-Replayed: true`) instead of running again. The same key with a different body is refused with 422. Only successful answers are remembered. Not applied to sign-in, sync, setup or account routes.
- **if_updated_at** (PUT body): the `updated_at` of the record as you loaded it. If the record has changed since, the save is refused with `409 { error, stale: true, updated_at }` and nothing is written. Omit it to save unconditionally. Successful PUTs return the new `updated_at`.
- **Client-record history** (1.17.0): `GET /api/clients/:id/history` returns `{ revisions, may_revert }`, newest first, each `{ id, at, by, via, reverts, reverted_by, changes: [{ field, label, before, after }] }`, for the client's care team and `records:manage-others` (anyone else 403, audited); on a device that syncs with an office 403 with `officeOnly: true`. `POST /api/clients/:id/history/:rev/revert` (the primary worker or `records:manage-others`; accepts `if_updated_at`) puts the change's fields back and answers `{ ok, updated_at, revision }`, or 409 with `changed_since` (field names) when a field has changed again since. `PUT /api/clients/:id` answers the new `revision`; a change notice's task carries `notice_revisions`.
- **Re-admission**: `POST /api/clients/check-duplicates` returns `readmit` (discharged records outside the caller's caseload that match on surname + date of birth or phone). `POST /api/clients/:id/readmit { first_name, last_name, dob, phone, reason }` assigns the caller, opens an episode and queues the event for supervisor review; the reason must be at least 8 characters.
- **A visit with its note**: `POST /api/interventions` accepts `note: { kind, format, title, content, structured, part2_protected }` (a client is required). The note is created as a draft linked to the visit, in the same transaction, under the notes permissions and rules; the response carries `note_id`. A refused note (403, or 400 with `fields.note_*`) saves nothing. `PUT` does not accept a note.
- **Time entries' source**: `GET /api/time` rows carry `source` (`visit`, `call` or `manual`); the list filters on `source=visit|call|manual` and, for `time:all`, `user_id`.
- **Approved time is locked** (1.15.3): `PUT` and `DELETE /api/time/:id` on an entry with status `approved` answer 409, for the worker and for `time:all` alike, and sync push refuses the same edit or deletion (`not permitted`, permanent). `POST /api/time/:id/approve` with `decision: "rejected"` and a `note` returns an approved entry to its worker (audited `time.rejected` with `reopened: true`); it can then be corrected and resubmitted.
- **County view** (built for 1.18.0, not yet released; office server only, [COUNTY-VIEW.md](COUNTY-VIEW.md)): `GET /api/county-submission/file?from&to&county_code&county_name&funds=id,id` (`reports:funder`, `budget:read`, `export:read`; the period must have ended, the funds be settlement funds) answers the signed county submission file, JSON `{ format: "suds-county-submission", schema_version: 1, payload, signature: { algorithm: "Ed25519", key_fingerprint, value } }`, the payload carrying `recipient: { county_code, county_name }` and the chosen funds only, the signature over its canonical serialisation (keys sorted, no whitespace); `POST /api/county-submission/key` makes the key without a file and `POST /api/county-submission/key/new` retires it for a new one. `GET /api/county/code` (`county:view`) is the county's code. `POST /api/county/submissions { text }` (`county:manage`) imports one: `201 { status: "imported" | "superseded" | "older", message, submission }` (`older`: kept, but a file made later counts), `200 { status: "duplicate" }`, or `422` (`413` when over 256 KB) `{ error, reason }` with `reason` one of `malformed`, `format`, `schema`, `period`, `recipient`, `unknown_key`, `inactive`, `signature`, `retired_key`; refusals are throttled per person (`429`). `POST /api/county/submissions/:id/withdraw { reason }` and `/reinstate`; `POST /api/county/programmes/:id/keys { public_key, fingerprint | compared, old_compromised }` replaces a programme's key and `PUT /api/county/programmes/:id/keys/:keyId { compromised }` marks a replaced one. `GET /api/county/view?from&to` (`county:view`) returns `{ programmes, rows, whole, part, none, of, headline, inactive_left_out, caveats, caveat_summary, rule, publication_note }`, each row `{ group, key, label, money, by: { programme_id: value | null }, total }`; `&by=quarter` returns `{ quarters, rows }` with `by_quarter` per row. `GET /api/county/view/export?from&to&format=xlsx|csv|tidy`.
- **County connection** (built for 1.18.0, not yet released; off by default; office server only, [COUNTY-VIEW.md](COUNTY-VIEW.md) *Connecting*). Machine routes, a bearer token and never a session, 404 while `county_connect_enabled` is off: `POST /api/county-connect/v1/submissions` (a connection token, `sudscc_…`; the body is the signed county submission file, at most 256 KB, read only for a live connection token) answers `201 { status: "imported" | "superseded" | "older", reason: null, message, period, receipt: { sha256, received_at } }`, `200 { status: "duplicate", … }`, or `422`/`413` `{ status: "refused", reason, message, receipt }` (`reason` the import's own, `recipient` and `retired_key` included, or `wrong_programme` when the file's key is another programme's than the token's; `message` the county view's words); `GET /api/county-connect/v1/status` (the same token) answers `{ county: { code, name }, programme, cadence, expected: [{ from, to, label, received, coverage }], outstanding, received: [{ from, to, sha256, received_at, generated_at, status }] }` (`code` the county's eight-character code a file must name; `label` as the Send to the county card names the period; counted by the combined view's rule, so a withdrawn, replaced or compromised-key file does not count); `GET /api/county-connect/v1/combined?from&to[&format=json|tidy-csv]` and `GET /api/county-connect/v1/programs` (a read token, `sudscr_…`) answer the combined view with `notes` (summed, not unduplicated; exact, internal, not for publication) and the programmes with their current key's fingerprint, their key history (fingerprints and dates) and the periods of their files that count. Wrong or missing tokens `401` (with `WWW-Authenticate: Bearer`), the wrong kind `403`, limits `429`. Signed in: `GET|PUT /api/county-connect/settings` (`county:view`; changing needs `county:manage` and `settings:manage`), `GET|POST /api/county-connect/tokens` and `POST /api/county-connect/tokens/:id/revoke` (`county:manage`; `POST` `{ scope: "county.submit", programme_id, expires_days? }` or `{ scope: "county.read", name, expires_days? }` answers the token once); on a programme's server `GET|PUT|DELETE /api/county-connect/connection` (`PUT`/`DELETE` `settings:manage`; the token is never returned), `POST /api/county-connect/connection/test`, and `POST /api/county-connect/send { from, to, funds?, county_code?, county_name? }` (`reports:funder`, `budget:read`, `export:read`; the file names the county's code from its status, and a `county_code` given must be it; `funds` default to those last chosen for that county, and none is refused) answering `{ status, reason, message, receipt, send }`.
- **Supplies catalog**: `GET /api/supplies/catalog` includes `can_configure` (the caller may add items here, so the visit form can offer to add the standard ones).
