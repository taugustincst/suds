# Data lifecycle: collection, retention, deletion, residency

## Residency and subprocessors

* **Data stays where the county hosts it.** SUDS is software the county runs on its own server, VM or cloud tenant. The records, backups, logs and anchors are written only to paths the county configures (`SUDS_DATA_DIR`, the offsite directory, `AUDIT_ANCHOR_DIR`). Choosing a US region / GovCloud tenant / on-premises host is the county's residency control.
* **No subprocessors.** The SUDS project operates no service: no hosted database, no telemetry, no analytics, no crash reporting to a vendor, no license server, no update service that receives data. Nothing is sent to the SUDS project or to GitHub by a running office server.
* **Outbound connections exist only when an administrator configures them** (`../DEPLOYMENT.md`, "Outbound internet"; `../HIPAA.md`): the county identity provider (OIDC; no PHI), Microsoft Graph for OneNote import (the county's own tenant, if used), the release feed (`UPDATE_FEED_URL`; no data sent), provider pictures for the resource directory (public websites; no PHI), a syslog collector for anchors (no PHI), and (1.17.0, off by default) the AI provider for the documentation copilot, which receives de-identified-where-known session text and is PHI (`../AI-COPILOT.md`: the programme's own BAA/QSOA with that provider is required first), and (1.18.0, off by default) the **county connection**: a programme's server posts its signed, aggregate county submission file to its county's SUDS server and reads what the county expects of it (no client-level data; `../COUNTY-VIEW.md`, *Connecting*). Each of these is the county's own service or a public website — none is a SUDS subprocessor; where PHI transits the county's Microsoft tenant, the county's BAA with Microsoft governs it.
* **What a county's server receives** (1.18.0): only its programmes' aggregate county submissions, by file or over the county connection, and it answers only its own systems' read API calls (expiring read tokens) with the combined aggregates. From 1.20.0 it may also hold figures its own staff entered or imported for a grantee not on SUDS (aggregate, in the same form, with the source document they came from, encrypted); these never leave the county's server except in its own view, files and read API, marked *entered by the county — not signed by the program* (`../COUNTY-VIEW.md`, *County-entered figures*). A county can run a county-only install that holds no client data at all (`../COUNTY-VIEW.md`, *A county-only install*).
* **What 1.23.0 changes here.** For the first time the office app keeps something in a browser: a street-outreach contact that names nobody (no client, participant code or notes), saved with no signal, waits in that phone's IndexedDB (`suds-outreach-queue`) until it is sent to the office, or the worker discards it; it is about no one, so it is not encrypted, it is kept per account and survives sign-out for that worker's next sign-in, and it never goes anywhere but the programme's own office server (`../USER_GUIDE.md`, *Street outreach*; `DATA-INVENTORY.md`). A worker's request to have their phone set up for the field is kept in the office server's settings (`field_request:<user id>`: when, its state and the ids of the administrators' to-dos; staff, not a client); it is not removed, and a request left open when the worker's account is deactivated keeps its to-dos open until an administrator closes them (an open item, `../../HANDOFF.md`, 1.23.0). A follow-up to-do now records the call or visit it follows (`tasks.call_id`, `tasks.intervention_id`, migration 67: ids only), retained and purged with the to-do.
* **What 1.22.0 changes here.** A county's publication release names only programmes whose written consent to publication the county has recorded (`county_publication_consents`: the date, the agreement's reference encrypted, who recorded and withdrew it), and each release keeps what it was screened from, encrypted (`county_publication_inputs`), so that a withdrawn release's period can be published again as an audited correction; both stay on the county's server and are kept as long as its publication record. A field device's scope now follows the account (`field_accounts`, which holds only the account and when; no PHI), so a device of an account held to the field scope holds the field scope whatever id it sends. A programme's county file is version 1 unless its county is known to read version 2, so the award leaves the programme only for a county that reads it. A passkey the authenticator allow-list stops has the date it stops stored on it (`passkeys.allowlist_grace_until`), cleared when the list is turned off. Nothing new leaves the programme.
* **What 1.21.0 changes here.** A county's server may **publish** a screened release of its combined figures (County view › Publish): aggregates, programme names and labels only, screened for small cells against every programme's own release; the county decides where it goes, and the record of what it published stays on its server (`../COUNTY-VIEW.md`, *Publication*). The county file now carries each fund's award amount and period (schema version 2; still aggregates). A **field device** holds only its worker's own recent caseload, without contact, intake, legal or clinical details, and removes what it may no longer hold at its next sync (`../PLATFORM.md`, *Field devices*). The **authenticator allow-list** makes no outbound call: the administrator downloads the FIDO Metadata Service file and loads it (`../FINGERPRINT.md`, *Authenticator allow-list*).
* **Participant codes (1.21.0).** A client may be known by a participant code alone (`clients.participant_code_enc`, encrypted, with a blind index); it is part of the client record, retained and purged with it, printed in the identified export and FHIR only through the disclosure gate, and never in the de-identified export.
* **Fingerprint sign-in (1.19.0) collects no biometric data.** The device's authenticator matches the finger; SUDS receives a public key at enrolment and signatures afterwards, so no biometric retention or destruction schedule applies (`../FINGERPRINT.md`).

### The GitHub Pages build ("SUDS on this device")

A second, separate way to run SUDS (`../WEB_APP.md`, `../PLATFORM.md`): the app's code is served from GitHub Pages and the records live only in that one browser, encrypted, with their keys beside them. GitHub never receives record data (no sync, no network calls with records), so it is not a business associate, but: the code is served by GitHub (a repository compromise could serve altered code — self-host the static build to remove that dependency), the records have no server-side copy (loss of the browser profile loses everything not in a device backup), and there is no central audit or retention. Counties that need central retention, audit review or residency controls should use the office server; a county may prohibit the on-device app by policy.

## Deletion

* **Soft delete** (with a required reason) is the everyday action for records staff remove, so an erroneous deletion is recoverable and audited.
* **Hard delete** happens by retention (above), by merge of duplicates, and by removal of fictional sample data. Retention deletes rows from every table at once, not just the client row, so nothing identifiable is left behind in child tables; financial and time rows keep their amounts with the client link removed.
* **Backups** age out by the retention count locally; offsite copies and backups taken before a purge still contain purged records until they expire — set the offsite store's retention to match policy.
* **Devices** are told what was deleted (tombstones); revoked devices can be wiped remotely at their next contact (`server/devices.js`).
* **Decommissioning** an installation: stop the service, destroy the data volume and every backup set, then destroy the keys (without `SUDS_ENCRYPTION_KEY`, any copy that survives is ciphertext — crypto-shredding). Record it in the county's disposal log (§164.310(d)(2)).

## Export and portability

Administrators and supervisors can export data (de-identified by default; identified exports require a recipient and purpose and write an accounting-of-disclosures row per client — `server/exports.js`, `server/disclosure.js`). The database is a standard SQLite file; with the keys, the county can read every record with its own tools. There is no lock-in to a vendor service.
