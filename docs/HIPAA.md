# HIPAA, 42 CFR Part 2 and security controls

SUDS is designed to help a covered entity meet the HIPAA Security Rule (45 CFR §164.308–.316), the Privacy Rule's individual-rights and de-identification provisions, and the confidentiality requirements for SUD records under 42 CFR Part 2. Software alone does not make a program compliant: policies, training, risk analysis, BAAs and physical safeguards are the program's responsibility. This document maps the technical safeguards SUDS provides to the rule, and lists what remains for the organization.

## Technical safeguards implemented

| Requirement | Implementation |
| --- | --- |
| **Access control — unique user ID** (§164.312(a)(2)(i)) | Every user has an individual account; shared accounts are not supported. API keys are separate, write-only, and named. |
| **Access control — emergency access** (§164.312(a)(2)(ii)) | Administrators may open a clinical note only by supplying a break-glass reason of at least 15 characters. Each use is written to the audit log (`note.view.breakglass`, `note.list.breakglass`) **and** queued in Supervision → Break-glass access, where a supervisor or privacy officer must acknowledge it (nobody can acknowledge their own). The count of unreviewed accesses appears on the supervisor's home page. |
| **Automatic logoff** (§164.312(a)(2)(iii)) | Server-side idle timeout (default 15 min, capped at 60, editable in Settings) and absolute session limit (12 h); the browser warns one minute before sign-out. Sessions are revoked on password change. |
| **Encryption at rest** (§164.312(a)(2)(iv)) | All direct identifiers and free-text PHI are encrypted with AES-256-GCM using a key held outside the database: names, DOB, phone, email, address, Medicaid ID, emergency contact, goals, safety flags, call summaries **and purposes**, visit summaries, note titles and content, structured note sections, addenda, **task titles**, referral **outcomes, barriers and notes**, overdose **substances** and notes, consent and disclosure recipients, purposes, scope and **justifications**, break-glass reasons, patient-request notes, episode presenting problems and discharge summaries, completed county forms and their attachments, imported text and titles, MFA secrets. Search on encrypted fields uses keyed HMAC blind indexes so ciphertext is never scanned. The database should additionally sit on an encrypted volume. |
| **Encryption in transit** (§164.312(e)) | Native TLS 1.2+ support (self-signed certificate generated by the setup wizard, or a supplied certificate) or a TLS-terminating proxy; HSTS; `Secure`, `HttpOnly`, `SameSite=Strict` session cookies. Network access from other devices cannot be enabled without HTTPS. |
| **Audit controls** (§164.312(b)) | Every authentication event, PHI read (client view, note view, list, timeline, export, accounting of disclosures), write, permission denial, configuration change and API-key use is recorded with user, IP, entity, client and details. Each entry carries a keyed hash chained to the previous entry. Once a day (and after every retention purge) the server **seals the head of the chain**: the newest entry's id and hash and the row count are HMAC'd with the index key, stored in settings, and written to the log file at info level. Verification (Administration → Audit log, and the daily scheduled check) walks the chain **and** compares it with the sealed head, so deleting the newest entries — which leaves a chain that still verifies — is reported as `truncated`. The daily check is incremental: it resumes from the last entry it verified (whose id and hash are sealed with the index key, so the marker cannot be moved by editing the database) and walks the whole chain once a week; the Verify button always walks the whole chain. Both read 5,000 entries at a time and let other requests run in between, so a million-row log no longer freezes the server while it is checked. Because someone who holds both the database and the index key could still rebuild the whole chain, the head is also **anchored outside the database** every 6 hours and at every backup (`server/audit-anchor.js`): a write-once file per anchor, sealed with the index key and naming the anchor before it, in `AUDIT_ANCHOR_DIR` (a WORM share in a proper deployment) and optionally a syslog collector; verification compares the chain with every anchor, so a rewritten chain is reported. An auditor can take the chain away as NDJSON with a signed manifest (`GET /api/admin/audit/export`) and check it offline (`npm run verify-audit-export`). Retention defaults to 7 years. |
| **Integrity** (§164.312(c)) | Signed notes are locked; a signature hash over the encrypted content is stored and can be re-verified. Only the note's author may sign it; a supervisor **countersigns**, which is recorded separately so the record always shows who provided the service and who approved it, each with its own verifiable hash. A device can never assert a countersignature. Corrections are addenda, never edits. Consents, disclosures and addenda are **insert-only through sync**: a device may add to the legal record and may revoke a consent, but a push that would alter or resurrect one is refused as `immutable`. Records are soft-deleted with a required reason. AES-GCM authentication tags detect ciphertext tampering. |
| **Person or entity authentication** (§164.312(d)) | scrypt-hashed passwords (N=2^15, computed off the request thread), 12-character complexity policy, forced change of temporary passwords, lockout after 5 failures (15 min), login rate limiting, TOTP multi-factor authentication (RFC 6238), timing-safe comparisons. Multi-factor is **required of every role by default** (`MFA_REQUIRED_ROLES`) and enforced: after a grace period (3 days by default, counted from creation or approval; settable to 0) an account can reach nothing but the enrolment screens until it is set up. |
| **Minimum necessary** (§164.502(b)) | Role-based permissions; navigators and clinicians see only clients on their caseload; finance and readonly see de-identified client codes only and hold neither `clients:read` nor (for readonly) `export:read`; clinical notes are visible only to clinical roles and supervisors. Exports require `export:read` (every role but readonly; a caseload-scoped role exports only its own caseload) and are de-identified unless the user holds the audited `export:identified` permission (supervisor, admin). The same limits apply to records a device uploads: every synchronised table carries the permission its API routes require, and caseload scoping is applied to pushed rows as well as pulled ones. |
| **De-identification** (§164.514(b)(2), Safe Harbor) | A de-identified export carries none of the eighteen identifiers. Every date is reduced to the **year**. Date of birth is never exported: it becomes an age band (0-17 … 65-89), and everyone over 89 is `90+`. ZIP codes are cut to their first three digits, and a three-digit area of 20,000 people or fewer (the 2000-Census list HHS guidance uses: 036, 059, 063, 102, 203, 556, 692, 790, 821, 823, 830, 831, 878, 879, 884, 890, 893) is written as `000`. The city column is omitted. Client codes are never written: each row carries a **record id** drawn at random for that export and never stored. It links a client's rows within one file (across every sheet of a workbook), is new in the next file, and cannot be traced back to the client. A de-identified dataset carries only an explicit allow-list of columns (`DEID_COLUMNS` in `server/exports.js`, justified column by column). Free text is not on it: names, notes, document and receipt references, vendors, locations, referral source or discharge reason typed in by hand, preferred language, a consent's expiry event, a disclosure's method, an episode's discharge disposition. A coded column (status, type, outcome, discharge reason, substance, gender, housing, insurance, referral source …) may only carry one of its codes (`DEID_CODED`). Any other value, such as a reason typed in before the field became a list, goes out as `other`. Durations worked out from two dates (days to engagement, minutes of service) are kept, because a duration is not an element of a date. Staff, fund, budget-line, provider and form-template names are kept, because they identify the programme, not the client. The outcome measures CSV follows the same rules. Files are labelled "De-identified (HIPAA Safe Harbor)" in the filename, the `X-SUDS-Export` response header and, for Excel, an *About* sheet. Text cells that a spreadsheet would read as formulas are neutralised. Safe Harbor also requires that the programme has no actual knowledge that what remains could identify someone (§164.514(b)(2)(ii)). That judgement is the programme's to make before a file is shared. |
| **Small cells in aggregate reports** | The funder report, the Naloxone Distribution Project log and the opioid settlement report suppress every count of people below the small-cell threshold (11 unless an administrator sets another, from 2 to 50), and are a **publication release** only for the whole programme and one standard period that has ended, labelled *Publication release — small cells screened; review before sharing*: the three reports for such a period are one release, audited as one constraint system with an exact integer solver, and checked against an attacker who knows the method; its files are exported only after the person exporting confirms they reviewed the withheld and small figures (recorded in the audit log with the release id). It is a conservative screen, not a guarantee and not an expert determination. The design, what it protects against and what it does not: [Small cells in aggregate reports](#small-cells-in-aggregate-reports) below. The other aggregate screens (dashboard, programme summary, monthly trends, episodes, referral outcomes, outcome measures) and row-level de-identified exports are **not** suppressed. |
| **Accounting of disclosures** (§164.528) | An identified export is itself a disclosure: it must name its recipient and purpose, and one accounting row (basis `export`) is written for every client it contains — one per client per file, so a workbook of a dozen sheets records one disclosure per client, and the workbook's own accounting sheet leaves those rows out. `GET /api/clients/:id/disclosures/accounting` (audited) and the **Print accounting** button on the Consents tab produce the accounting a client is entitled to. |
| **Individual rights** (§164.522, .524, .526, .528) | Requests for access, amendment, restriction or an accounting are recorded on the client's **Requests** tab with the date received; each carries a 30-day due date, is flagged when overdue, and is closed as fulfilled or denied with a note (encrypted). |
| **Retention and disposal** (§164.316(b)(2), §164.310(d)(2)) | Discharged client records (every episode closed), and records left inactive, are hard-deleted from every table by a daily job once their **last activity** is older than the retention period — `client_retention_years`, default 7, never below 6. Last activity is the latest date anywhere on the record: intake, discharge, episode opened or closed, and every visit, call, note, addendum, referral, to-do, consent, disclosure, form, overdose event, patient request, time entry or expenditure linked to it — so outreach logged years after a discharge keeps the record for another full period. Active and waitlisted records are never purged. Devices receive tombstones. An administrator can place a record on **legal hold**, which exempts it from the purge and blocks deletion until the hold is cleared (both audited). The purge is audited by client code only. |
| **Transmission of application security** | Content-Security-Policy (self only, no inline scripts), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on every response, CSRF protection via a required custom header on state-changing requests, JSON body limits, request timeouts, no third-party scripts or CDNs. The only outbound connections are ones an administrator configures: the optional Microsoft Graph (OneNote) connector, single sign-on discovery and key fetches from the configured identity provider, the optional release check (`UPDATE_FEED_URL`, only when clicked), and pictures for resource-directory entries loaded from a starter region file. The browser's own connect-src policy is `'self' https:` so those can work; no third-party script ever loads. |
| **Supply chain** | Zero third-party runtime packages; only Node.js built-ins. |

## Small cells in aggregate reports

`server/publication-release.js`, `server/sdc.js`, `server/small-cells.js`, `server/funder-report.js`, `server/harm-reduction-reports.js`; the figures themselves in [compliance/HARM-REDUCTION-REPORTING.md](compliance/HARM-REDUCTION-REPORTING.md). Safe Harbor is about identifiers, not cell sizes: whether a small count could identify someone in a report shared outside the programme is a question for statistical expert determination (§164.514(b)(1)). What SUDS does is a conservative, documented default, not a determination.

**What is suppressed.** Every count of people above 0 and below the threshold *T* is shown as `<T` (primary suppression): people served and each demographic row, people per fund and per settlement use, referrals, admissions, MAT, episodes and discharge reasons, overdose events and reversals (an event happens to one person), fatal and community-reported overdoses, who gave the naloxone. Zero stays 0. Counts of naloxone kits, test strips, services, staff hours and money are not counts of people and stay exact. Naloxone doses are not people either, but every reversal records at least one dose and at most 20, so the doses used bound the reversals: in a publication release they are cells of the audit, hidden with the reversals (or events) they would reveal. A median length of stay over fewer than *T* discharges is `suppressed`.

**One release, audited as one system.** A publication release is not three reports suppressed separately. For one standard period that has ended (below), the funder report, the NDP log (by month) and the opioid settlement report are **one release** (`server/publication-release.js`): their figures are read together in one synchronous pass (nothing else writes in between), every count of people any of them prints goes into one constraint system, and the audit decides every cell of all three at once. Each report then prints its part; all three carry the same `release.id`, a digest of everything the release prints. The audit is deterministic, so asking again, or for the export, gives the identical release. (1.12.1 suppressed each table on its own and linked them by hand, and two leaks followed: the settlement report printed 20 people for a use whose fund the funder report had hidden with the total, which gave away 10 men and 10 women; and a month whose reversals were shown `suppressed` (at least 11) beside 11 events was worked out to be exactly 11, which gave away the other month's `<11` as 5.)

*The attacker.* Knows the rule and reads every number of the release. A number is an equality. `<T` is a count from 1 to *T*−1 (zero is printed as 0). `suppressed` on a count of people is at least *T* (a smaller one would have been `<T`); on a figure hidden with it (a fund's services) at least 0. `withheld` is unknown. The attacker also knows every relationship between the true counts (`server/publication-release.js` lists them; each holds for the true figures by construction and the audit checks that it does): each breakdown adds up to the people served; on MAT, referred, admitted, each fund, each settlement use and each race code are at most the total; the race codes together are at least the total, and *unknown* plus any other code at most it; a fund's or a use's people are at most its services (everyone served was served at least once); a use's people are at least each of its funds' and at most their sum, and its services are exactly theirs (a settlement fund no longer active, which the funder report does not list, is an unprinted count tied in); events by month add up to the events, reversals by month and by who gave the naloxone add up to the reversals, a month's reversals are at most its events, fatal and community-reported events are at most the events, and fatal plus reversed events are at most the events (true for everything recorded through SUDS, where a fatal event is saved as not survived; left out for a period where an imported row breaks it); discharges add up by reason; the episodes opened in the period are at most those closed in it plus those open at its end, since each is one or the other (left out for a period holding an episode that closes before it opened: the close route refuses one, but a fatal overdose dated before the episode opened, or an import, can still record one); the doses used in a month's reversals lie between its reversals and 20 times them and add up to the NDP total, and all doses used are at least those used in reversals, at most 20 per event, and the rest at most 20 per event not reversed (each left out for a period whose records break it, such as a reversal saved with no dose). Which rows are listed, and in what order, is published too: see below. Counts nobody printed but anyone can work out are counts of people too, and sensitive when small: the people left when on MAT, referred, admitted, a fund, a use or a race code are taken from the total; a use's people not under one of its funds; events not reversed (in total and in each month), not fatal, not community-reported, and neither reversed nor fatal; the episodes carried in from before the period (closed plus open at the end, minus opened).

*Which rows are listed, and in what order.* The rows a table lists are published as surely as its numbers. 1.12.2 listed only the rows that were not zero - a month only if it had an overdose, an NDP month only if it had a reversal, a discharge reason or a "given by" code only if it was used - so a listed row said "at least 1" even when its value was `withheld`, and an unlisted NDP month said "exactly 0". One reversal by staff in each of ten months was printed as ten `withheld` NDP rows and `staff <11`: ten rows of at least one, at most ten in all, so exactly one a month. Two designs were weighed: modelling presence (every listed row at least 1, an unlisted one 0) keeps the tables short, but the row set still tells the reader which categories were used and every future table has to be modelled the same way; listing a **fixed set of rows** makes the row set say nothing. SUDS does the second, and models what is left. In a publication release every month of the period is listed in the funder report's overdoses by month and in the NDP log's reversals, and every code of the "given by" and discharge-reason lists (as the programme has set them up) is listed, zero or not. A key outside the list (a code imported from elsewhere, a month an event's UTC date puts outside the period) is listed only because it is not zero, and the model says so (at least 1). A table withheld whole prints **no rows at all**, never rows marked `withheld`. A true 0 is printed as 0: it says that nobody had that count, which is all a zero says, and the audit treats it as a known value, so it never narrows a hidden count beyond the rule. A zero is never hidden as a complement (`suppressed` means at least *T*, which it is not); when only zeros are left near a count, its table is withheld instead. Rows are listed in a fixed order (the list's, or by key), never by size: rows sorted by count, as 1.12.2 printed them, say which of two hidden counts is the larger. The free-text breakdowns (gender, language, housing, insurance and ethnicity as typed; race codes as stored) have no fixed list: each lists only the keys with people, and a withheld one lists none. At most ten keys under *T* are listed per breakdown, the first ten by key whatever their counts; the rest are combined in one row, **Other (combined)**. That keeps the audit small whatever an import wrote (1.12.2 took 20 s to audit 800 one-person languages, once per report) and keeps a rare value from being printed as a label beside a small count; which keys are combined says nothing about their counts.

*The protection rule.* A sensitive count - a `<T` cell, or a withheld or unprinted count of people that the printout lets be from 1 to *T*−1 - is protected only if the release is consistent with it being **1** and with it being ***T*−1**: the release as a whole says nothing about it that `<T` alone does not. "1 and *T*−1" means as near them as the printout's symbols alone allow: served `<11` beside women `<11` and men `<11` says there are at most 9 women whatever else is printed, so there 9 is the upper value (the symbols are 0, `<T`, and "at least *T*" for a number or `suppressed`; which rows are listed, and in what order, is not a symbol). Whether an unprinted count is sensitive is decided from its feasible range given what would be printed, never from its true value (1.12.3 checked the people not on MAT only when that number was truly small, which is how 12 beside `<11` came to mean exactly one). A cell hidden to protect another (`suppressed`) must still range over at least ⌈*T*/2⌉ values. Why this rule and not "cannot be pinned to one value" (1.12.0 and 1.12.1): narrowing a small group to "1 or 2", or "exactly *T*−1 or *T*−2", is most of a disclosure, and a rule that tolerates it has to reason about how much narrowing is too much; requiring the full range removes the question. The complementary cells are not themselves sensitive (each is at least *T*), but one that can be read off to within a few is in effect published, and whoever relies on the release should not find hidden cells that are not hidden.

*The pattern of what is hidden.* SUDS is open source, so an attacker knows the method, not just the rule: it can run the audit on every programme that could lie behind a printout and keep those whose printout is identical. The pattern of what is hidden is then information. Against 1.12.3 (review of 1.12.4): 12 served with 1 on MAT printed 12 and `<11`, with 2 on MAT `suppressed`, so 12 beside `<11` meant exactly one; events 12 beside reversals `<11` meant exactly one reversal; and a withheld table said the total was not 1, or that everyone served was on MAT. The cause: which unprinted counts were checked, and which complement was picked first, depended on true values the release does not print.

The standard sufficient condition is that the pattern, given the primary pattern (which cells are `<T` and which 0, themselves printed as symbols), is a function of the printed values and the structure alone: then every world consistent with the printout prints the same release, and the check against the printout is the check against the method. SUDS meets it where it can: whether a count must be protected depends on its feasible range given what would be printed, never on its true value; a total whose parts are all small is hidden by the symbols alone; the candidate order is structural; no search starts from a true value, so each answer is a function of the question. It cannot meet it everywhere, and no rule that keeps a useful total can: hiding a cell because of its own value tells that its value is one of those that would be hidden. With 1 to 10 on MAT, 11 served shows the people not on MAT as 1 to 10 (protected), 12 to 20 would pin them (so they are hidden), and 21 or more says nothing; a hidden total there says "12 to 20", which is fine for the total but tells that the people not on MAT are at least 2. Hiding the total always whenever any subset is small would satisfy the condition, and publish almost no totals. So the release is checked against the method directly (`server/sdc.js` `consistent()`): for every cell it hides - `<T`, `suppressed`, withheld, and the cells of a fund no longer active - SUDS finds worlds with the same printed figures and the hidden counts linked to that cell changed as little as possible, runs each through the same suppression, and keeps only those that print the identical release; a `<T` or withheld cell is protected only if such worlds show it can be 1 (the lowest value its symbols allow: the one person) and range over at least ⌈*T*/2⌉ values, and a `suppressed` count only if two such worlds put it at least ⌈*T*/2⌉ apart. A release in which any cell is not shown protected is **refused**. Against the method this asks less than "1 and *T*−1", which is still asked against the printout: a hidden total that is shown only when large takes *T*−1 off a `<T` part (discharges hidden only between 12 and 20, beside `moved <11`, say that at most 9 moved) without saying anything about who is in the group; requiring *T*−1 there refused ordinary months. To make that pass where it should, an unprinted count that the symbols let be *T* or more must not be shown to be under *T* by the numbers beside it either (11 served beside `<11` on MAT is hidden like 12: otherwise a hidden total would say "not 11"). What this proves and what it does not: each world found prints this release through the suppression; that it would also pass the check itself is not proved (its own search starts from its own figures). Counts printed nowhere but worked out from printed ones (the people not on MAT, the events not reversed) are held to the rule against the printout, not against the method on every release: asking it of them refused ordinary releases, such as a 5,000-person year, for want of a world rather than for a leak found. The tests hold the whole release, refusals included, to the rule on every world of small families (below).

`test/publication-release.test.js` has the algorithm-aware attacker (`test/fixtures/pattern-attacker.js`): for small programmes - people served and a subset, up to 25 people at *T* = 11 (and every *T* = 3 and 5 size to 19); women, men and MAT; overdose events and reversals in one month and in two; two funds, with people under one, both or neither - it enumerates every world, runs the real release on each, groups them by printout, and checks every hidden cell over the worlds of its group (each hidden cell must be able to be 1 and range over ⌈*T*/2⌉ values; every count printed nowhere must range over ⌈*T*/2⌉ small values). Families are enumerated well beyond the sizes checked, so a group is not cut off at the edge. Against 1.12.3 it fails on the reviewer's cases (12 served printed as 12 with one on MAT and `suppressed` with more; at *T* = 3, a `<3` total that could only be 2); against 1.12.4 it finds none.

What it costs: releases the check cannot show protected are refused. At the default threshold the 5,000-person year, a month of 20 people split 10 and 10, and the quarters of the review publish; a tiny programme at a small threshold often does not (about seven in ten of the property test's random programmes of 1 to 12 people at *T* = 3 to 5 are refused; publish a longer period). A refusal publishes nothing but says that this period's figures could not be shown protected.

*The solver.* Every check is decided over the **integer** solutions, exactly. A linear-programming relaxation is not enough on its own: the integer solutions lie inside the LP's, so a wide LP range does not prove a wide integer range - it would say "protected" where it may not be. The relationships are not totally unimodular in general (two breakdowns of the reversals, the month links, the settlement links and the race-code cover together), so integrality cannot be assumed either. `server/sdc.js` answers each question (can this count be 1? *T*−1? what is the least and greatest value of this hidden cell?) by branch and bound over a small dense two-phase simplex (Bland's rule), on only the hidden cells connected to the one in question; visible cells are constants. Almost every LP is integral at once, so the search is tiny; one that runs past its node budget answers "not protected", never "protected". No dependencies.

*Verified, or refused.* When the hiding stops - because nothing is under-protected, or because it gave up (its step limit, nothing left to withhold) - every sensitive count is checked again, all of them, exactly, and then every hidden cell against the method (above; at most 400 worlds are run for one release, and a search that runs out answers "not shown"). Only a release in which every one passes is published. One that does not, or an audit that runs past its time limit (5 s; it runs synchronously), is **refused**: the funder report, the NDP log, the settlement report and their files answer 422 with a message saying the period cannot be published, and nothing is labelled a publication release. Internal runs and the programme's own submission, for the roles that may run them, are unaffected; a longer period usually passes. (1.12.2 gave up and published: with the search budget forced to one node, 111 of 150 random programmes leaked.) The audited release is kept for five minutes, keyed by everything the audit reads, so the three reports of one release and their files run the audit once, and a changed figure is always audited afresh.

*The fixpoint.* Primary cells are hidden as `<T`. A total every non-zero part of which is `<T` (women `<11`, men `<11`) is hidden too, with every count of at least *T* that is part of it (the people under a fund), whatever their values: printed, it would say how the small parts add up, and hiding it only when that pins them would say by the hiding that it is not the one value that does not. Then, while some sensitive count is under-protected, one more cell is hidden (`suppressed`): among the cells in the relationships that bind it, in a fixed structural order - nearest first, a breakdown's cells before its total, people before other figures, then the model's order (table order, then key order), never by value (1.12.3 broke ties by the true count) - the first that fixes it, else the first that helps, else the first. The audit then runs again. Cells only ever go from shown to hidden, so it stops. A figure that is not a count of people but bounds one (a fund's or a use's services) is hidden with its people. When nothing visible is left to hide, the table that pins the count is **withheld** whole (listed in `release.withheld`; demographic breakdowns also in `withheld`). A total and a complete visible breakdown of it are the same published number, so the total is hidden only with at least one cell of every breakdown that would print it. `test/publication-release.test.js` attacks random small programmes - several funds, settlement uses, an inactive settlement fund, overdose months with fatal and reversed events and doses, episodes opened and carried in, small thresholds - and the 1.12.2 review's shapes (one reversal a month, many discharge reasons, episodes mostly still open, many doses per reversal) with an attacker that shares no code with the engine (a finite-domain search with bounds propagation over every number all three reports publish, including the NDP rows read a second time, which rows are listed and in what order, and the doses) and checks the rule for every hidden and every small unprinted count. It replays the 1.12.1 and 1.12.2 findings through the API, and checks that a release the audit cannot finish is refused. The same attacker finds 1.12.2's leaks. A year for 5,000 people is read, audited and checked against the method in under 2 seconds (0.6 to 1 s in the tests; the check is most of it), and 800 one-person languages with 400 one-person race codes audited in under 1.5 (`test/publication-release-perf.test.js`).

What the rule costs: a total whose breakdown is all `<T` is hidden, with the counts of at least *T* under it; a total beside a small subset is hidden when the rest would be pinned between 1 and *T*−1; and releases the check cannot show protected against the method are refused (above). Publish a longer period, or combine groups, when that happens. Listing every month and code costs rows of zeros, and combining rare free-text values costs their labels.

Runs that are not publication releases (fund-filtered, caseload-scoped, custom-range or unfinished; `purpose=submission` or `internal`) keep the per-report suppression of 1.12.1 (`server/small-cells.js`): each table protected with its own total, not audited across reports. They are labelled not for publication.

*The label, and the confirmation.* A publication release is labelled *Publication release — small cells screened; review before sharing* on screen, in its counting statement, on its files' About sheet (Purpose) and in their filenames (`…-publication-screened-review-before-sharing`); 1.12.3 said "suitable for publication", which promised more than a screen can. Its files (the funder report, the NDP log and the settlement report, `/export`) are exported only when the request confirms the review (`reviewed=1`; the page asks for the tick box *I have reviewed the withheld and small figures before sharing*); without it the API answers 428 with that message, and with it writes `report.publication.reviewed` to the audit log with the report, the period and the release id. Internal and submission files are exported as before. The `X-SUDS-Report-Purpose` header stays `publication`.

**Across releases: what may be published.** Suppression inside one report cannot stop two reports being subtracted from each other: the whole programme (34 served) minus a run filtered to fund A (33) is the one person served under fund B only, and women 14 minus 13 says she is a woman; January–June minus January–May is the people first served in June. So only one shape of run carries the **publication** label: the **whole programme** (no fund filter, no caseload scope) for **one standard period that has ended** — a calendar month, a quarter (starting January, April, July or October), or a year starting on one of those quarters (a July–June or October–September fiscal year, or a calendar year). Everything else — a fund-filtered, custom-range, caseload-scoped or unfinished run — is **internal, not for publication**, says so on screen, on its About sheet and in its filename (`…-internal-suppressed`), and asking for `purpose=publication` on it is refused. It is still suppressed unless someone holding `reports:exact` asks for exact counts for the programme's own submission or internal use. **Who may run a run that is not a publication release** (funder report, NDP log, settlement report; `server/auth.js` `reportRunAllowed`, checked in `server/routes/reports.js`): holders of `reports:internal` (supervisor, administrator), or a role with `clients:read` whose run counts only clients it can open anyway (a navigator's or clinician's own caseload; the whole-programme settlement report only when caseloads are not restricted). Finance and readonly run publication releases only, so neither can difference an internal run against a release; finance's money and staff hours are exact in a release and on Funding & spending. `reports:exact` is held only with `reports:internal` (supervisor, administrator). A refused run is audited as `authz.denied`. Each funder gets its own fund's figures that way: as the programme's **submission** to that funder, which is not publication. Publicly, per-fund people served appear only in the whole-programme release's *By funding source* table, audited with the programme total. Published, the NDP log is aggregated **by month**, and its reversals are the funder report's reversals by month in the same release; the day-by-day log by site is for the programme's submission to the NDP. The settlement report's people per allowable use are cells of the same release, audited with the funder report's total and funds. A navigator's or clinician's caseload run counts only the caseload: people served, people per fund and overdose events are the caseload's clients', and events reported from the community (no client) are left out (the report says so).

| Role | Publication release | Internal / submission run (suppressed) | Exact counts |
|---|---|---|---|
| Administrator, supervisor | yes | yes (`reports:internal`) | yes (`reports:exact`) |
| Navigator, clinician | caseload runs are internal | own caseload only (funder report, NDP log) | no |
| Finance | yes | no | no |
| Read-only | yes | no | no |

**Whom suppression protects against.** Small-cell suppression protects a **publication release against its recipients** - funders, the public, anyone who has the release and no other access to SUDS. It is not a control against the programme's own staff. An account holding `reports:read` or `export:read` is an insider: it can already open the dashboard and the monthly trends report (`/api/reports/monthly`: exact whole-programme counts by month, including overdose events and reversals), and with `export:read` (held by finance and the front-line and supervisory roles; not by read-only) row-level de-identified exports (`/api/reports/export/:kind`, HIPAA Safe Harbor), any of which says more about a small group than a suppressed cell hides. Against insiders the controls are workforce policy, least-privilege role assignment and the audit log: the dashboard (`report.dashboard`), the monthly trends report (`report.monthly`), every de-identified or identified export (`report.export`) and every funder, NDP and settlement run are audited. As defence in depth, internal and submission runs of the three reports need `reports:internal` (or a caseload-scoped role counting only its own caseload), so read-only and finance accounts get publication releases only (table above).

**Residual risk, stated plainly.**

* Standard periods nest: a quarter lies inside its year, a month inside its quarter, and a July–June year overlaps an October–September one. Two publication releases for nested or overlapping periods (Q1 and the year, or the year and its first three quarters) can still be subtracted from each other. Preventing that needs suppression coordinated across releases, which SUDS does not do. **Publish one standard period per funder cycle** (for example the fiscal year, once), and use submissions, not publications, for anything finer.
* Running the same period again after late entries changes its figures; the two versions subtract to the late entries. Publish each period once, after its data are complete.
* A funder that receives the programme's fund-filtered submission can subtract it from the public whole-programme release. That is the funder's own data; the submission is labelled not for publication or sharing, and the funder's agreement should say so.
* Anyone with access to internal or exact runs (fund-filtered, custom-range, `counts=exact`) can subtract them from a release, and staff with reporting or export access have other, finer views (above). That is governed by permissions (`reports:internal`, `reports:exact`, `export:read` in `server/auth.js`), role assignment and the audit log, not by suppression; internal runs are labelled not for publication.
* The attacker model is what the release prints plus the relationships listed above. Outside knowledge (a neighbour who knows someone was served, a figure published elsewhere) is not modelled. Sums of several small cells of one breakdown (the people who are not men, when two gender rows are `<11`) are not protected as a group, as is usual for a threshold rule.
* The hiding is greedy: it may hide more than an optimal pattern would. It never hides less than the rule requires, and a release it cannot verify is refused, not published.
* A relationship left out because the period's records break it (an imported fatal reversal, a reversal saved with no dose, an episode closed before it opened) is left out for that period: an attacker who assumed it would be reasoning from something false, but one who knows which records were imported may know more.
* **The pattern of what is hidden.** The suppression pattern of any deterministic method can tell an attacker who knows the method more than the printed numbers do (above). 1.12.4 decides which counts to protect from what would be printed, takes candidates in a structural order, hides a total whose parts are all small by the symbols alone, and checks every hidden cell of every release against worlds that print the same release through the same suppression, refusing the release otherwise. What remains: the check proves that its witness worlds print the release through the suppression, not that they would pass the check themselves; counts printed nowhere (the people not on MAT) are checked against the method only by the tests' families, not on every release; a refusal says that the period could not be shown protected; nested or overlapping periods, outside knowledge and the zeros a release prints are outside it, as above. A zero is printed: "0 on MAT" or "everyone served under one fund" is published when true.
* Rounding (for example random rounding to base 5) would blunt differencing between releases but is not implemented. **This is a conservative default, not a statistical expert determination** (45 CFR 164.514(b)(1)); no statistical expert has reviewed the method. Before publishing, review the release - the export asks the person to confirm it, and records that - or combine groups.

## 42 CFR Part 2

The rule-by-rule matrix against the **2024 final rule** (compliance date 16 February 2026), with file and route references and what the programme must supply itself, is [compliance/PART2.md](compliance/PART2.md). In short:

* **Part 2 programme setting** (`part2_program`, on by default; Privacy & Part 2 → Overview). While on, the client header carries the **42 CFR Part 2** label, a general release (ROI) is not accepted as consent, and everything that leaves the programme carries the §2.32 notice. Notes default to `part2_protected` and are labelled on screen and on paper.
* **Consents** capture every §2.31 element and the server refuses a Part 2 consent that lacks any of them: who may disclose, recipient (a name or a class), purpose, the information covered (scope), the right to revoke and how, an expiration (a date **or** an event), who signed (the patient, or a named parent, guardian or representative — §2.14/§2.15), evidence it was signed (a document reference, a witness, or "signed on paper"), the redisclosure statement, and the consequences of refusing to sign. Four Part 2 types: a named disclosure, the 2024 rule's **single consent for treatment, payment and health care operations**, a consent for **SUD counseling notes** only (§2.31(b)), and a consent for use in a **legal proceeding** only (§2.31(d)). Each consent prints as a PDF with every element. Consents recorded before the 2024 element list are marked *Pre-2024 form*.
* **Every disclosure goes through `server/disclosure.js`**: referrals (on creation, update and outcome), manual disclosures, and identified exports. It is refused without a live consent of the right type or another lawful basis; a consent cannot be stretched beyond its type (a TPO consent never covers counseling notes or a proceeding); a **court order** basis needs a recorded subpart E order for that client that states the required findings and met the notice requirement, is in force and not vacated; information **for use in a proceeding against the patient** needs such an order or a proceedings-only consent (§2.12(d)); **SUD counseling notes** need their own consent or an order that covers them; and a client's **agreed restriction** (§2.26) must be confirmed as checked. A referral that shares nothing — left pending, with no warm handoff — needs none.
* **Lawful bases other than consent** (§2.51 medical emergency, subpart E court order, qualified service organisation, audit/evaluation, research, crime on premises, child-abuse reporting) can be recorded by any role that records disclosures. A **medical emergency** must carry a written justification (at least 20 characters). **"Other"** is a supervisor/administrator override (`disclosures:override`) and must also be justified. Justifications are stored encrypted with the disclosure and appear in the accounting.
* **Revoking a consent** flags every open referral that relied on it. Revocation is the only change a synchronising device may make to a consent.
* **Accounting of disclosures** (§2.25 / HIPAA §164.528): each disclosure records recipient, purpose, information disclosed, method, legal basis, justification where required, the consent or court order relied on, whether it was for a legal proceeding or included counseling notes, and which §2.32 notice version went with it. Printable for the client from the Consents tab.
* **Identified exports** must name the recipient and purpose and state a lawful basis (`consent` — every client in the file needs a live Part 2 consent — `audit_evaluation`, `research`, `qsoa` or `internal`); a proceeding is never a bulk export. One accounting row per client; the file carries the §2.32 notice (Excel: the About sheet; CSV: the last row). An export naming more clients than the threshold opens a draft incident. De-identified exports follow Safe Harbor and are not Part 2 records.
  * The **county EHR hand-off** is an identified disclosure too. It keeps its own basis choice — each client's consent (clients without one are left out and listed), a QSOA, or a justified supervisor/administrator "other" — with the same consent types as a consent-based export (the single TPO consent qualifies; a general release only outside a Part 2 programme), the same agreed-restriction confirmation, the §2.32 notice in the file, and the mass-export incident.
  * The **CalOMS Tx submission** is required by law: it is recorded under the fixed `state_reporting` basis (no basis to choose, no consent checked, not stoppable by an agreed restriction) when the submission file is produced, against that file's id and SHA-256, with the §2.32 notice in its README and the mass-export incident (on producing it and on each download). The preview carries no names or dates of birth and is not accounted. Every one of these rows records the notice version, `legal_proceeding = 0` and `counseling_notes = 0`.
* **FHIR API** (docs/integration/FHIR.md): every FHIR answer that identifies a client is a disclosure to the organisation the FHIR client was registered for, made under the same rules as `requireBasis`. It is made only for clients with an active, unexpired, unrevoked consent that can authorise a disclosure here — a Part 2 consent naming that organisation for the purpose of use, or the single TPO consent naming it (alone or within a class); a general release only when `part2_program` is off — and no agreed restriction; others are omitted (and never confirmed to exist). SUD counseling notes are never listed, and note text is never sent. Each response carries the `R` / `42CFRPart2` / `NORDSLCD` security labels and the 2024 §2.32 notice, and one accounting row is written per client per request with the notice version. A bulk export is checked and accounted when each file is downloaded, not when it is built: a file naming a client whose consent has lapsed since the build is not released. FHIR clients authenticate at the token endpoint only (SMART Backend Services `private_key_jwt`, or a client secret the administrator may switch off); the secret is never itself a bearer token.
* **§2.32 notice** in the 2024 wording (`PART2_REDISCLOSURE_NOTICE` in `server/constants.js`): shown to the worker with every disclosure made under consent, and printed on exports, completed-form PDFs, consent PDFs, the accounting and printed notes.
* **§2.22 patient notice**: an administrator-editable, versioned notice of privacy practices (a built-in starting text covers the 2024 elements); each time a client is given it is recorded (date, method, by whom, version, acknowledgement). The Overview, Home and Privacy & Part 2 → Notice not given show who has not had it.
* **§2.4 complaints**: a complaint log (supervisors and administrators) with encrypted summary and resolution, whether the complainant was told they may complain to HHS, and a no-retaliation check; never deleted.
* **Breach notification** (§2.16 as amended, applying 45 CFR §§164.400–414): an incident register with the four-factor risk assessment, the determination and its reason, and computed deadlines — individuals within 60 days of discovery, HHS at once for 500 or more (otherwise the annual log), media for more than 500 in one state. Home warns within 14 days and when late. A failed audit-chain check, a break-glass access flagged at review, and a very large identified export open a draft incident automatically.
* Consent and court-order text, disclosure recipients and content, justifications, notice notes, complaint summaries and incident narratives are stored encrypted like any other PHI — who a client's records may be shared with is itself sensitive.

## Browser local mode (the offline copy) and sync

* The web application on the office server is the system of record (docs/PLATFORM.md). The native phone apps were removed in 1.9.3; what follows describes the browser's local mode, which is **off by default** from 1.9.3 and which a county turns on deliberately — the setup wizard's offline-copy question, or `LOCAL_MODE_ENABLED=true` — only for a documented field-work need.
* A local-mode browser stores its own database in that browser profile, sealed at rest: the whole image is AES-256-GCM encrypted under a key that is wrapped by the device account's password (PBKDF2-SHA-256, 600,000 iterations), and the `*_enc` column keys are sealed under it too (`security/ENCRYPTION-AND-KEYS.md`, *On-device build*; ADR-0008). It is locked after every page load, on sign-out and when idle. While someone is signed in the records are open on the device, and a copied profile can be attacked offline at the PBKDF2 rate, so local mode still belongs only on county-managed devices with a device passcode, disk encryption and MDM remote wipe, and only for the people and devices the county has approved.
* Sync transmits records over HTTPS to the office server, authenticated with the user's office credentials (and MFA where enabled); PHI is decrypted for transport and re-encrypted with the receiver's own key. Credentials are not stored on the device; each sync uses a short-lived session.
* The server enforces minimum necessary on sync: only the user's caseload is downloaded; clinical notes, ASAM assessments and outcome measures (screening answers) only for clinical roles; MFA secrets and other users' credentials are never sent. Uploads are attributed to the syncing user, cannot change approvals or signed notes, cannot alter or delete consents, disclosures or addenda (a consent may only be revoked), cannot delete clients or notes, and are rejected outside the caseload. Every sync is audited on the server, including the device's own audit entries. Break-glass events are reviewed on the office server and are not synchronised.
* The office server is authoritative: permanent sync rejections are final and the device stops resending them; a purged or merged record cannot be resurrected from a device; each office account has its own sync cursor on a device. Every local-mode browser that syncs is listed under Settings → Synced devices, where an administrator can revoke or wipe it; deactivating an account or resetting its password queues a wipe for its devices. With local mode off (the default; `LOCAL_MODE_ENABLED=false` or the wizard's *No*), the server serves an explanation instead of the kernel.

## SUDS on this device (the web app on GitHub Pages)

* From 1.9.5 the GitHub Pages build is a production way to run SUDS for people without an office server (`WEB_APP.md`). Its records are stored in one browser on one device, sealed exactly as local mode stores them (the whole database encrypted under a key only a device account's password opens), and never leave the device: there is no sync, and the app sends no record data anywhere.
* **Access control on the device.** Accounts are created on the device with Sign up; the first one manages the device and can turn further sign-ups off. Later accounts are navigator accounts, and once there is more than one account every navigator and clinician sees only their own caseload. Passwords follow the same policy as the office server; every sign-up, sign-in, backup and restore is in the device's hash-chained audit log.
* **Availability and integrity (§164.308(a)(7)).** The records exist only on the device, so the contingency plan is the device backup: an AES-256-GCM file keyed by PBKDF2-SHA256 (600,000 iterations) from a passphrase the person chooses, holding the database and its keys, restorable only with that passphrase, refused if altered. The first-run Sign up states where records are kept and requires the person to confirm it; Home reminds the device's manager after 7 days without a backup; the app asks the browser for persistent storage and shows whether it was granted.
* **Hosting.** GitHub serves the app's code only. No PHI reaches GitHub, so no Business Associate Agreement applies to the hosting, but a county using the on-device app should record in its risk register that the code is served from GitHub (or self-host the build, `WEB_APP.md`).

## Risk register notes

Residual risks a county should carry in its own risk register (§164.308(a)(1)). None is a defect; each is a consequence of a design choice, stated so it is weighed rather than discovered.

| Risk | What it means | Mitigation in place / what the county does |
| --- | --- | --- |
| **Blind-index equality and frequency leakage** | The `_idx` columns (`last_name_idx`, `full_name_idx`, `first_name_idx`, `preferred_name_idx`, `name_prefix_idx`, `first_name_prefix_idx`, `name_phonetic_idx` — a Soundex code —, `dob_idx`, `phone_idx`) are deterministic HMACs. Anyone holding the database file *without* the keys cannot read a name, but can see which rows share a value: which clients have the same surname, date of birth or phone number, how common each value is, and (from the three-letter prefix and Soundex columns) coarse groupings of similar names. Frequency analysis against a public name list can suggest likely surnames for the commonest values. | The keys never sit beside the database in a proper deployment (secrets manager or `data/keys.json` excluded from IT backups); the database is on an encrypted disk; backups are themselves AES-256-GCM encrypted, so a stolen backup leaks nothing, indexes included. Treat a copy of `suds.db` without its keys as a limited disclosure of *relationships*, not as harmless. |
| **One key, two uses: index key and audit chain** | `SUDS_INDEX_KEY` keys both the blind indexes and the HMAC that chains and seals the audit log (`server/audit.js`). Someone who has the index key (for example to run a search-side tool) could also forge a consistent audit chain; rotating one rotates the other (`npm run rotate-index-key` re-signs the chain). | Documented, not yet separated: deriving a distinct audit key (HKDF of the index key with its own label) needs a one-time re-sign of every existing chain and a matching change in the browser kernel, so it is scheduled as its own change rather than folded into another. Until then, give the index key the same custody as the encryption key, and keep the sealed-head checkpoint line in the collected log (it lives outside the database). |
| **Single instance, single SQLite file** | One process and one database file (DEPLOYMENT.md, "Single instance only"). No high availability: a host failure is an outage until the host or a restore is back. | Scheduled, off-host, encrypted backups; a recovery drill (`npm run dr-drill`, or Settings → System & backups) that restores the newest backup into a throwaway copy and records the measured RTO and RPO; a warm standby procedure (DEPLOYMENT.md, "County hosting options"); a bigger host rather than replicas. |
| **Device copies: open while signed in, and only as strong as the password** | The on-device database is sealed at rest under a key wrapped by each device account's password (ADR-0008; until then the keys sat in `localStorage` beside a database stored in the clear). What remains: while someone is signed in, the records and key are in the page's memory (malware, or an unlocked unattended device); a copied profile can be attacked offline at the PBKDF2-SHA-256 (600,000 iterations) rate, which a weak password does not survive; a forgotten password with no other account and no backup loses the device's records. | Local mode is off by default from 1.9.3. Where it is on: county-managed devices only, with passcode, disk encryption and MDM remote wipe; revoke/wipe from Settings → Synced devices; deactivation queues a wipe (PLATFORM.md). The password policy (12+ characters, mixed) applies to device accounts; sign out when the device is put down. |
| **On-device app: records in one browser** | SUDS on this device (GitHub Pages) keeps its records only in the browser that holds them, with the keys beside them. Clearing the browser's site data, a browser evicting storage, or a lost or broken device loses every record not in a backup; anyone who can use the browser profile can read them. The code is served from GitHub, with which there is no BAA (none is needed for code that never receives PHI), and a compromise of the repository or the Pages site could serve altered code. | First-run confirmation of where records are kept; encrypted device backups with a 7-day reminder; persistent-storage request and status; caseload scoping between accounts on one device. The county: decides whether the on-device app may hold client information at all, requires device passcode/disk encryption/MDM, sets a backup routine and where backup files are kept, records the GitHub hosting (or self-hosts the build), and prefers an office server where records must be shared or retained centrally. |
| **Experimental runtime module** | `node:sqlite` is experimental in Node 22 and 24. | CI runs the suite on Node 24 in advance; migration plan in DEPLOYMENT.md ("Node.js support and the move to 24"). |

5. **Contingency plan** — run the encrypted backups (docs/DEPLOYMENT.md) and test restores.

7. **Patient requests** — answer access, amendment, restriction and accounting requests within the 30 days the Requests tab tracks; a denial must be given to the client in writing.

9. **Breach notification** — record every possible breach in the incident register (Privacy & Part 2 → Incidents & breaches) on the day it is discovered; SUDS computes the 60-day, HHS and media deadlines and will not close a breach until the notices are recorded, but the risk assessment, the determination, the notices themselves and any substitute notice are the programme's, with counsel.
10. **Physical safeguards** — server room / cloud region controls, workstation placement.
11. **42 CFR Part 2 policies** — counsel-approved consent, revocation and patient-notice wording; a complaint procedure (§2.4) with no retaliation; security and breach policies (§2.16); staff training on the 2024 changes (TPO consent, counseling notes, the bar on use in proceedings, court orders). ## Key management

* `SUDS_ENCRYPTION_KEY` and `SUDS_INDEX_KEY` are 256-bit keys supplied by the environment, or generated into `data/keys.json` (mode 0600) on first run for installations without an IT-managed secret store. In that case the administrator must download the key backup (Administration → System) and store it separately from database backups. Rotate with `NEW_ENCRYPTION_KEY=<hex> npm run rotate-key` during a maintenance window (server stopped, backup taken). Never commit keys.
* Backups are encrypted with a key derived from the encryption key; store keys and backups separately.

## Resource pictures
Pictures on treatment center profiles are meant to show buildings, entrances and rooms. They are not PHI and are stored unencrypted alongside the resource record so they can be shown quickly and synced to local-mode devices. Staff are reminded in the app never to upload pictures of clients; if one is uploaded by mistake, remove it from the profile (audit-logged) and note the incident per your policy.

## County forms
Filled-out forms and attached signed copies are PHI: their values and files are stored encrypted (AES-256-GCM) with the client record, every view, print and attachment is audit-logged, and access follows the same caseload rules as notes. Blank templates in the form library are not PHI and are shared with every device. Printed PDFs carry a Part 2 / HIPAA handling notice; treat paper copies per your program's policy.
