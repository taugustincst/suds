# Identity and access

## Authentication options

| Method | Status | Code |
| --- | --- | --- |
| Username + password | Always available unless SSO is required; scrypt hashes; 12+ characters with upper, lower, digit, symbol; expiry after 90 days by default (`password_max_age_days`); temporary passwords must be changed at first sign-in | `server/auth.js` `login`, `passwordPolicy`; `server/routes/auth.js` |
| Single sign-on (OIDC) | Optional; Authorization Code + PKCE with one county identity provider (Entra ID, Okta, Keycloak, ADFS 2016+ with OIDC…). Accounts are linked by an administrator (`oidc_subject`), or — for an account SCIM provisioned — on its first sign-in by the provider's object id (`oid` = SCIM `externalId`) or username (`preferred_username`/`upn`/verified `email` = SCIM `userName`); a sign-in never creates or promotes an account | `server/oidc.js`, `server/routes/oidc.js` |
| Identity provider's MFA in place of SUDS TOTP | **Off by default.** Settings → Security policy → *Trust the identity provider's multi-factor sign-in* (`sso_trust_idp_mfa`). An SSO sign-in whose ID token carries `amr` `mfa`, or `amr` values naming two factors of different RFC 8176 kinds (knowledge `pwd`/`pin`/`kba`; possession `otp`/`sms`/`tel`/`hwk`/`swk`/`sc`; inherence `fpt`/`face`/`iris`/`retina`/`vbm` — e.g. `pwd`+`otp`, `hwk`+`pin`), or an `acr` listed in `sso_mfa_acr_values` (also sent as `acr_values` to ask for it), completes without the SUDS code. A lone `otp`, `hwk` or `swk` (or two of the same kind) does not count: each can be the only factor at the provider; the session is marked `mfa_source='idp'` and is exempt from the SUDS enrolment deadline. A sign-in the provider does not mark as multi-factor still needs the SUDS code. Every such sign-in is audited (`auth.oidc.login`, `details.mfa = "idp"` with the `amr`/`acr`), turning it on or changing the acr list is audited on its own (`security.idp_mfa_trust`), and Security status shows it with the count of IdP-MFA sign-ins in 30 days | `server/oidc.js` `idpMfa`; `server/routes/oidc.js` `mfaTrust`; `server/auth.js` `requireAuth`; `test/idp-lifecycle.test.js` |
| SCIM 2.0 provisioning | Optional. `/scim/v2/Users` for Entra ID / Okta user provisioning, authenticated by a bearer token scoped `scim` (Settings → Security status → *Provisioning (SCIM)*); see *Directory integration* below | `server/scim.js`, `server/routes/scim.js`; `test/scim.test.js` |
| **SSO required** | Settings → Security policy → *Require single sign-on* (`sso_required`). Password sign-in is refused (HTTP 403, audited `auth.login.sso_required`) for every account except the named **emergency (break-glass) administrator accounts** (`sso_emergency_accounts`). Refused unless OIDC is configured and each named account is an active administrator. Emergency sign-ins are audited with `emergency_account: true` and logged as warnings | `server/auth.js` `ssoPolicy`, `login`; `server/security-status.js` `validateSettings`; `test/security-evidence.test.js` |
| TOTP two-step verification (RFC 6238) | Required for every role by default (`MFA_REQUIRED_ROLES`), with a grace period for new accounts (**3 days** by default — `MFA_GRACE_DAYS`, or `mfa_grace_days` in Settings; 0 = at first sign-in), counted from the account's creation or, for an access request, its approval. It was 14 days up to 1.11.0; approval restarting the clock meant every approved account had a fortnight of password-only access. Past the deadline the account is not locked out: it can still sign in, load the app shell (`/api/meta/constants`, `/api/me/prefs`, no PHI) and reach the enrolment endpoints, the app sends it straight to enrolment (*My profile* → *Enroll authenticator*), and every other request is refused with `mfaSetupRequired` (`test/mfa-grace.test.js`, `scripts/ui/signup.mjs`). Settings → *Require two-step verification for every role* (`mfa_require_all`) makes it an explicit switch that overrides the role list. The MFA secret is stored encrypted | `server/auth.js` `requireAuth`, `mfaDeadline`, `policy` |
| API keys | Write-only intake keys (hashed), named, revocable; cannot read data | `server/routes/admin.js`, `server/routes/intake.js` |
| Metrics token | Bearer token for `/api/metrics` only; no PHI | `server/metrics.js` |

**Break-glass accounts for an IdP outage.** Name at least one (preferably two) administrator accounts in `sso_emergency_accounts`. They keep a password (and TOTP): seal the credentials (sealed envelope in a safe, or the county's privileged-access vault), review every use (Audit log → filter `auth.login`, look for `emergency_account`), and rotate the password after each use.

**SSO and MFA together.** By default an SSO sign-in still passes SUDS's own TOTP step for roles that require it, so a county that enforces MFA at the IdP sees a second prompt. A county whose identity provider enforces MFA for SUDS (an Entra ID conditional-access policy, an Okta sign-on policy) can turn on *Trust the identity provider's multi-factor sign-in* instead; SUDS then relies on the provider's assertion in the ID token, which it verifies (RS256 signature against the provider's published keys, issuer, audience, expiry, nonce). Do not turn it on unless the provider really enforces MFA for this application: SUDS can only check that the provider *said* MFA was used. Keep the break-glass accounts on SUDS TOTP.

**Signing as a single sign-on user.** The electronic signature asks the signer to prove again who they are once the quick-signing window (`sign_reauth_minutes`) has passed. An account linked to the identity provider that has no SUDS password (SCIM-provisioned) and no SUDS authenticator is offered *Confirm with single sign-on* instead of a password field (`GET /api/auth/reauth` → `method: "sso"`; a linked account that also has a password gets it as an alternative). `POST /api/auth/oidc/reauth` starts an Authorization Code + PKCE round-trip with `prompt=login` and `max_age=0`; the callback accepts it only if the ID token verifies, names the same `sub` as the account, carries an `auth_time` no earlier than the start of the round-trip (60 s clock skew allowed; a provider that hands back an existing sign-in is refused) and the session that asked is still live (it is named in the signed state cookie, since the `SameSite=Strict` session cookie does not travel on the provider's redirect back). Then that session's `reauth_at` is set and the browser returns to the note (`?sso_reauth=ok`). Every outcome is audited (`auth.oidc.reauth`). If the provider cannot be reached the dialog says so and the note stays a draft (`server/routes/oidc.js`; `test/oidc-reauth.test.js`).

## Sessions

* Server-side sessions; the cookie carries a random 256-bit token, only its SHA-256 is stored (`server/auth.js`).
* Idle timeout 15 minutes by default (`session_idle_minutes`, capped at 60), absolute limit 12 hours (`session_absolute_hours`); the browser warns a minute before sign-out; background polling does not count as activity.
* Password change revokes the account's other sessions; a user can revoke their own other sessions; deactivating an account ends its access.
* `HttpOnly; SameSite=Strict; Secure` cookie; state-changing requests need the `X-Requested-With: suds` header (CSRF).

These are visible in Settings → Security policy and on Settings → Security status.

## Brute force and enumeration

Account lockout after 5 failures for 15 minutes; 20 failed sign-ins per source address per 15 minutes (`LOGIN_RATE_LIMIT`); 10 MFA attempts per user per 10 minutes. The password or authenticator code given to sign a note (`auth.verifySigner`) counts toward the same lockout and limits, a locked account cannot sign at all, and a failed signature attempt ends the session's quick-signing window. Each authenticator code is accepted once — at sign-in, at signing or at enrolment — and never one from a time-step at or before the last one accepted (`users.totp_last_step`, RFC 6238 §5.2; `test/signer-hardening.test.js`); API 600 requests/min per address; unknown usernames pay the same hashing cost and get the same answer; the audit log records unknown usernames only truncated and hashed (`server/auth.js` `auditUsername`).

## Authorisation

Role-based, least privilege (`server/auth.js` `PERMS`): admin, supervisor, clinician, navigator, finance, readonly. Navigators and clinicians see only their caseload (`caseloadFilter`, `canAccessClient`). Finance and readonly see de-identified client codes only. Administrators are system administrators, not treating staff: opening a clinical note requires a written break-glass reason, is audited and queued for a supervisor's acknowledgement (`../HIPAA.md`). Every denial is audited (`authz.denied`).

## Account lifecycle

* Creation by an administrator, or a self-service *request* on the sign-in page that an administrator must approve and assign a role to (`POST /api/auth/signup`, can be switched off).
* Deactivation revokes sessions and queues a remote wipe of the person's local-mode devices (`server/devices.js`).
* **Deprovisioning by absence.** Settings → Security policy → *Disable single sign-on accounts not seen for (days)* (`sso_deprovision_days`, 0 = off). Once a day an active account linked to the identity provider (an OIDC subject or a SCIM `externalId`) that the provider has not vouched for in that many days — no SSO sign-in and no SCIM update leaving it active (`users.idp_seen_at`; before that, its last sign-in or creation) — is disabled, its sessions revoked and its devices revoked with a wipe on their next sync, audited as `user.deprovisioned`. Emergency accounts are never touched. The report (who is due, who is due within 7 days, who was disabled in the last 90 days) is on Security status and at `GET /api/admin/security/deprovisioning`; *run now* is `POST /api/admin/security/deprovisioning/run` (users:manage) (`server/deprovision.js`).
* **Accounts without two-step verification** — role, whether it is required, deadline, overdue, SSO-linked, last sign-in — are listed on Settings → Security status and at `GET /api/admin/security/mfa-report` (users:manage, audited).
* Access reviews: the Users & roles tab lists every account with role, MFA and last sign-in; a periodic review is a county procedure (see [SOC2-READINESS.md](SOC2-READINESS.md), CC6.2/6.3).

## Directory integration

**SCIM 2.0** (RFC 7643/7644) user provisioning, just enough for Entra ID and Okta: `GET /scim/v2/Users` (with `filter=userName eq "…"`, `externalId eq "…"` or `id eq "…"`, and `startIndex`/`count`), `POST /scim/v2/Users`, `GET`, `PUT`, `PATCH` (Entra's `"op":"Replace","path":"active","value":"False"` and Okta's value objects) and `DELETE /scim/v2/Users/{id}`, and `GET /scim/v2/ServiceProviderConfig`. Errors are SCIM error objects; responses are `application/scim+json`.

* **Set-up.** Security status → *Provisioning (SCIM)* → *Create a SCIM token* (users:manage; shown once, stored hashed, revocable, `last_used_at` recorded). In Entra ID: Enterprise application → Provisioning → Automatic, Tenant URL `https://<suds-host>/scim/v2`, Secret token = the token. In Okta: the app's Provisioning → SCIM 2.0, base URL the same, authentication *HTTP Header* (Bearer). The default attribute mappings work (`userName`, `displayName`/`name`, `emails`, `active`, `externalId`).
* **Roles.** SUDS keeps no Groups resource: group membership arrives as the user's `roles` or `groups` values (map *appRoleAssignments* or group names to `roles` in Entra; an Okta group-push attribute) and is mapped through `scim_group_roles` (`SUD Navigators=navigator; SUD Supervisors=supervisor`). Several mapped groups: the most privileged role wins. No mapped group: `scim_default_role` (readonly unless set). Role changes are audited with from/to.
* **Deactivation.** `active=false` (PATCH or PUT) or `DELETE` disables the account, revokes its sessions at once and revokes its local-mode devices with a wipe on their next sync (`scim.user.deactivate`). Accounts are never deleted: the audit trail refers to them. `active=true` reactivates.
* **Limits.** A provisioned account has no password (it signs in through OIDC, which links it on first sign-in). Emergency (break-glass) accounts cannot be changed or deactivated by SCIM (403, `mutability`). No bulk, no sort, no ETags, no Groups endpoint. Every create, update and deactivation is audited under the token's name (`scim:<name>`), and refused calls as `scim.denied`.

Without SCIM, disabling a person at the IdP stops new sign-ins immediately when SSO is required; *deprovisioning by absence* (above) then disables the SUDS account after the configured number of days, or an administrator deactivates it at once.

**Why not SAML.** SUDS supports OIDC, which Entra ID, Okta, Ping, Keycloak and ADFS (2016 and later) all offer, so a county identity provider can always be connected. SAML 2.0 would need XML canonicalisation and XML-DSig signature verification; there is no implementation of either in Node's standard library, and SUDS has no runtime dependencies by design (a hand-written XML-DSig verifier is a well-known source of signature-wrapping vulnerabilities). A county on SAML only can put an OIDC bridge in front (Entra ID, Okta and Keycloak all federate SAML to OIDC).
