# Identity and access

## Authentication options

| Method | Status | Code |
| --- | --- | --- |
| Username + password | Always available unless SSO is required; scrypt hashes; 12+ characters with upper, lower, digit, symbol; expiry after 90 days by default (`password_max_age_days`); temporary passwords must be changed at first sign-in | `server/auth.js` `login`, `passwordPolicy`; `server/routes/auth.js` |
| Single sign-on (OIDC) | Optional; Authorization Code + PKCE with one county identity provider (Entra ID, Okta, Keycloak, ADFS 2016+ with OIDC…). Accounts are linked by an administrator (`oidc_subject`), or — for an account SCIM provisioned — on its first sign-in by the provider's object id (`oid` = SCIM `externalId`) or username (`preferred_username`/`upn`/verified `email` = SCIM `userName`); a sign-in never creates or promotes an account | `server/oidc.js`, `server/routes/oidc.js` |

An SSO sign-in whose ID token carries `amr` `mfa`, or `amr` values naming two factors of different RFC 8176 kinds (knowledge `pwd`/`pin`/`kba`; possession `otp`/`sms`/`tel`/`hwk`/`swk`/`sc`; inherence `fpt`/`face`/`iris`/`retina`/`vbm` — e.g. `pwd`+`otp`, `hwk`+`pin`), or an `acr` listed in `sso_mfa_acr_values` (also sent as `acr_values` to ask for it), completes without the SUDS code. A sign-in the provider does not mark as multi-factor still needs the SUDS code. | SCIM 2.0 provisioning | Optional. `/scim/v2/Users` for Entra ID / Okta user provisioning, authenticated by a bearer token scoped `scim` (Settings → Security status → *Provisioning (SCIM)*); see *Directory integration* below | `server/scim.js`, `server/routes/scim.js`; `test/scim.test.js` |
| **SSO required** | Settings → Security policy → *Require single sign-on* (`sso_required`). Password sign-in is refused (HTTP 403, audited `auth.login.sso_required`) for every account except the named **emergency (break-glass) administrator accounts** (`sso_emergency_accounts`). Refused unless OIDC is configured and each named account is an active administrator. Emergency sign-ins are audited with `emergency_account: true` and logged as warnings | `server/auth.js` `ssoPolicy`, `login`; `server/security-status.js` `validateSettings`; `test/security-evidence.test.js` |
| TOTP two-step verification (RFC 6238) | Required for every role by default (`MFA_REQUIRED_ROLES`), with a grace period for new accounts (**3 days** by default — `MFA_GRACE_DAYS`, or `mfa_grace_days` in Settings; 0 = at first sign-in), counted from the account's creation or, for an access request, its approval. It was 14 days up to 1.11.0; approval restarting the clock meant every approved account had a fortnight of password-only access. Past the deadline the account is not locked out: it can still sign in, load the app shell (`/api/meta/constants`, `/api/me/prefs`, no PHI) and reach the enrolment endpoints, the app sends it straight to enrolment (*My profile* → *Enroll authenticator*), and every other request is refused with `mfaSetupRequired` (`test/mfa-grace.test.js`, `scripts/ui/signup.mjs`). Settings → *Require two-step verification for every role* (`mfa_require_all`) makes it an explicit switch that overrides the role list. The MFA secret is stored encrypted | `server/auth.js` `requireAuth`, `mfaDeadline`, `policy` |
| Passkeys (fingerprint sign-in and signing) | Released in 1.19.0; office server only; on by default, switchable (`passkey_signin`, `passkey_signing`), and *Require fingerprint or authenticator for signing* (`sign_strong_required`, off by default). A passkey with UV is multi-factor (NIST SP 800-63B AAL2): it satisfies `MFA_REQUIRED_ROLES`, and can finish a password sign-in. Lockout, rate limits and *Require single sign-on* (emergency accounts excepted) apply. No biometric data reaches SUDS. [FINGERPRINT.md](../FINGERPRINT.md) | `server/webauthn.js`, `server/passkeys.js`, `server/routes/passkeys.js`; `test/fingerprint.test.js` |
| API keys | Write-only intake keys (hashed), named, revocable; cannot read data | `server/routes/admin.js`, `server/routes/intake.js` |
| Metrics token | Bearer token for `/api/metrics` only; no PHI | `server/metrics.js` |

**Break-glass accounts for an IdP outage.** Name at least one (preferably two) administrator accounts in `sso_emergency_accounts`. They keep a password (and TOTP): seal the credentials (sealed envelope in a safe, or the county's privileged-access vault), review every use (Audit log → filter `auth.login`, look for `emergency_account`), and rotate the password after each use.

**SSO and MFA together.** By default an SSO sign-in still passes SUDS's own TOTP step for roles that require it, so a county that enforces MFA at the IdP sees a second prompt. A county whose identity provider enforces MFA for SUDS (an Entra ID conditional-access policy, an Okta sign-on policy) can turn on *Trust the identity provider's multi-factor sign-in* instead; SUDS then relies on the provider's assertion in the ID token, which it verifies (RS256 signature against the provider's published keys, issuer, audience, expiry, nonce). Do not turn it on unless the provider really enforces MFA for this application: SUDS can only check that the provider *said* MFA was used. Keep the break-glass accounts on SUDS TOTP.

**Signing as a single sign-on user.** The electronic signature asks the signer to prove again who they are once the quick-signing window (`sign_reauth_minutes`) has passed. An account linked to the identity provider that has no SUDS password (SCIM-provisioned) and no SUDS authenticator is offered *Confirm with single sign-on* instead of a password field (`GET /api/auth/reauth` → `method: "sso"`; a linked account that also has a password gets it as an alternative). `POST /api/auth/oidc/reauth` starts an Authorization Code + PKCE round-trip with `prompt=login` and `max_age=0`; the callback accepts it only if the ID token verifies, names the same `sub` as the account, carries an `auth_time` no earlier than the start of the round-trip (60 s clock skew allowed; a provider that hands back an existing sign-in is refused) and the session that asked is still live (it is named in the signed state cookie, since the `SameSite=Strict` session cookie does not travel on the provider's redirect back). Then that session's `reauth_at` is set and the browser returns to the note (`?sso_reauth=ok`). Every outcome is audited (`auth.oidc.reauth`). If the provider cannot be reached the dialog says so and the note stays a draft (`server/routes/oidc.js`; `test/oidc-reauth.test.js`).

## Sessions

* Server-side sessions; the cookie carries a random 256-bit token, only its SHA-256 is stored (`server/auth.js`).
* Idle timeout 15 minutes by default (`session_idle_minutes`, capped at 60), absolute limit 12 hours (`session_absolute_hours`); the browser warns a minute before sign-out; background polling does not count as activity.
* Password change revokes the account's other sessions; a user can revoke their own other sessions; deactivating an account ends its access.
* `HttpOnly; SameSite=Strict; Secure` cookie; state-changing requests need the `X-Requested-With: suds` header (CSRF).

These are visible in Settings → Security policy and on Settings → Security status.

## Brute force and enumeration

Account lockout after 5 failures for 15 minutes — a failure is a wrong password *or* a wrong authenticator code (sign-in's second step, enrolment and signing alike), and for an account with two-step verification a correct password does not reset the count: only the second factor does, so signing in again between guesses gains nothing; a locked account cannot finish signing in with the right code either. 20 failed sign-ins per source address per 15 minutes (`LOGIN_RATE_LIMIT`); 10 MFA attempts per user per 10 minutes, one bucket shared by `/mfa/verify`, `/mfa/enable` and signing. **Enrolment** (`/api/auth/mfa/setup`, `/mfa/enable`) is only for a fully signed-in session of an account that does not have two-step verification yet — the forced enrolment after the grace period is exactly that — and a failed enrolment code is audited (`auth.mfa.enable.failed`). Up to 1.12.4 a session still owing its second factor could use `/mfa/enable` to guess the account's existing code with no limit or audit, and a right guess completed the sign-in (`test/mfa-enrol-hardening.test.js`). The password or authenticator code given to sign a note (`auth.verifySigner`) counts toward the same lockout and limits, a locked account cannot sign at all, and a failed signature attempt ends the session's quick-signing window. So do the current password given to change it (`/api/auth/password`) and the password and code given to turn two-step verification off (`/api/auth/mfa/disable`, which since 1.14.0 needs a current authenticator code as well as the password; someone who has lost the app asks an administrator to reset it): each failure is audited (`auth.password.change.failed`, `auth.mfa.disable.failed`) and counts toward the lockout (`auth.confirmPassword`, `auth.confirmCode`). Up to 1.13.0 both took unlimited guesses from inside a session (`test/in-session-guessing.test.js`). Each authenticator code is accepted once — at sign-in, at signing or at enrolment — and never one from a time-step at or before the last one accepted (`users.totp_last_step`, RFC 6238 §5.2; `test/signer-hardening.test.js`); API 600 requests/min per address; unknown usernames pay the same hashing cost and get the same answer; the audit log records unknown usernames only truncated and hashed (`server/auth.js` `auditUsername`).

## Authorisation

Role-based, least privilege (`server/auth.js` `PERMS`): admin, supervisor, clinician, navigator, finance, readonly. Caseload scoping (`caseloadFilter`, `canAccessClient`, `caseloadRestricted`) applies to a role with `clients:read` and without `clients:all`. From 1.16.0 navigators and clinicians hold `clients:all` by default (and navigators `notes:clinical:read`, read only; clinicians `budget:read`), so a programme that wants a person held to their caseload denies them `clients:all` with a per-user override (1.15.0, `user_permission_overrides`; deny always wins), and the scoping then applies to that person everywhere it applied before, their devices' sync included (`test/role-expansion.test.js`): a local-mode device receives the person's own overrides and the office's caseload restriction with every sync and applies them, and removes what it pulled before a deny at its next sync (`test/sync-scope-change.test.js`). The role defaults scope no navigator or clinician; the programme default does. From 1.17.0 a programme setting, **New navigators and clinicians start held to their caseload** (Settings → Users & permissions, administrators only), gives every account that becomes a navigator or clinician a per-user deny of `clients:all` with the reason "programme default: held to caseload", audited per person: an administrator creating it, an approved access request, SCIM provisioning, a role change (by an administrator or by SCIM) into either role, and the device administrator of SUDS on this device creating one or changing its role (a device sign-up is held whatever the setting says, and denied clinical notes too). Single sign-on creates no account: its first sign-in links the account SCIM provisioned, which was held then. It is **on for a new install** and **off for an office upgraded from an earlier release**, so an upgrade changes nobody's access; Users & permissions recommends turning it on while it is off. It changes no existing account: the one-off *Apply to existing navigators and clinicians* lists exactly who will change and denies them `clients:all`, audited per person (a person granted `clients:all` individually is left alone). Only `clients:all` is denied: a navigator keeps reading clinical notes (the 1.16.0 decision), which a per-user deny of `notes:clinical:read` takes away. Moving an account out of navigator and clinician lifts the default's own deny, never an administrator's (`server/caseload-default.js`, `test/least-privilege-default.test.js`). With the setting off (an upgraded office that has not turned it on), an administrator who does not apply the deny gives that person every client. Seeing is not managing: changing or deleting another worker's records, recording work under another worker's name, removing a client record and seeing another worker's staged imports is `records:manage-others` (1.16.0; supervisors and administrators, who held it through `clients:all` before), which the REST routes and sync push both enforce (`server/rules/`, `server/crud.js`). From 1.16.1 it also governs deleting SUPRT-A assessments and CalOMS records, voiding or removing another worker's client forms and attachments, supply lines on another worker's visit, a goal's or step's wording and committing another worker's staged import; discharging or re-admitting is the client's care team's, the episode's opener's or `records:manage-others`' (from 1.16.3 the opener off the care team ends only their own assignment and to-dos: ending the rest of the team and discharging the client are the care team's or a manager's, at both doors; from 1.16.4 that standing cannot be regained by sync without `assignments:manage`: a worker's own assignment is taken only on a client the same push creates, and a push's re-admission restores the care team only when it lands); and on sync a record's creator is the account that syncs it, never a user a device names (security review of 1.16.0; `test/security-1161.test.js`, `test/sync-attribution.test.js`). SUD counseling notes are read only by their author, their co-signer and holders of `notes:clinical:write` (1.16.1; `notes:clinical:read` alone and break-glass do not open one; docs/compliance/PART2.md). Separation of duties: nobody approves their own time or spending, nor (1.16.1) an entry they recorded for someone else or changed, read from the audit trail; from 1.16.2 that covers the expenditure and time a visit or call records or resizes, and time they submitted for the worker. Nobody authors or signs a note as someone else, by sync either: a note's author is the account that syncs it, and a device's signature is refused unless it is the author's own (1.16.2), dated no earlier than the note and no later than the office's now, and a draft carries no signature columns (1.16.3). It is rated sensitive in the catalog and can be granted only to a role that records client work (never finance or read-only). On SUDS on this device, each account that signs up after the first is given those denies (`local/kernel.js`, `SIGNUP_SCOPE`). Finance and readonly see de-identified client codes only: neither holds `clients:read`, and `canAccessClient` refuses every single-client check for a role without it (before 1.13.0 the de-identified roles were exempt from caseload scoping *and* passed that check, so readonly's `forms:read` opened any client's filled forms). `forms:read` is the form library; a client's filled forms also need `clients:read` and the client on the caseload. `test/deidentified-roles.test.js` hits every GET route with real record ids as each role without `clients:read` and fails on any name, date of birth, phone, address or email in the response. Report runs are separate permissions (`../HIPAA.md`, "Small cells in aggregate reports"): `reports:internal` and `reports:exact` (supervisor, administrator) for internal runs and exact counts; `reports:funder` (supervisor, administrator and, since 1.14.0, finance) for the programme's own submission of the funder report, the NDP log and the settlement report — exact aggregate counts by fund and for any range, with no client-level data, audited with the purpose, fund and period. `reports:funder` gives finance no client record, no identified export and no unmasked dashboard. Read-only runs publication releases only, and nothing while an administrator has switched publication releases off.Administrators are system administrators, not treating staff: opening a clinical note requires a written break-glass reason, is audited and queued for a supervisor's acknowledgement (`../HIPAA.md`). Every denial is audited (`authz.denied`).

**Per-user permission overrides.** An administrator (Users & permissions tab) can grant a single permission a user's role lacks, or deny one the role holds, with a written reason (10 to 300 characters, about the person's job and never a client: it is kept with the override for administrators to read, and since 1.15.4 the audit log records only its length and SHA-256). Effective permissions = role defaults ∪ grants − denies, computed on every request (`server/auth.js` `effectivePerms`); a deny always wins, including across `namespace:*` wildcards and the write-implies-read rule. Changes apply to the user's next request with no re-login; the API is `GET/POST/DELETE /api/users/:id/permissions` (`users:manage`; audited as `user.permission.grant`, `user.permission.deny` and `user.permission.revoke`; refused attempts as `user.permission.denied`). Revoking an override needs a reason too (`DELETE` with `{ reason }`, the same bounds). Guards: an administrator may change their own permissions, role and account as they change anyone's (the owner's decision, released in 1.23.6 under a recorded policy exception, docs/RELEASE.md *Record: 1.23.6*; until then they could not), each such change audited exactly as one to someone else, with `self: true` in its details. It follows that a per-user deny placed on an administrator is advisory: the administrator may remove it (audited, with `self: true`); to restrict what an administrator can do, change their role instead. What makes that safe is the lockout guard (`server/auth.js` `lockoutProblem`): any change, to oneself or to another (a role change, a deny, removing an override, a deactivation, one's own included), that would leave the programme with no active account able to manage users and permissions is refused ("This would leave no active administrator who can manage users. Give another account that access first."), and the refusal audited (`user.permission.denied` or `user.update.denied`). It applies on SUDS on this device too (`PUT /api/local/accounts/:id`). Provisioning (SCIM) and single sign-on deprovisioning are not held back by it: the identity provider decides who has left, and the emergency (break-glass) accounts, which provisioning never touches, are the way back in. What a role may be granted at all is one rule (`server/permissions.js` `grantProblem`), applied when the grant is made, when the person's role changes (the grants the new role may not hold are removed, each audited as `user.permission.revoke` with `cause: role_change`) and at every request (`effectivePerms` ignores such a grant, so a row left behind or put in by hand does nothing): `users:manage`, `settings:manage` and `apikeys:manage` only for a user whose role is `admin` (to make someone a full administrator, change their role; security review of 1.15.3, M2: a demoted account kept `users:manage` and promoted itself back; an administrator who changes their own role away from `admin` therefore cannot change it back themselves); a de-identified role (finance, read-only: `clients:list-deidentified` without `clients:read`) is never granted `clients:read`, `clients:write` or `export:identified`; `clients:list-deidentified` is never granted to a role that opens records (M1); and `records:manage-others` (1.16.0) only to a role that records client work (`clients:write` in its defaults), never finance or read-only. Unknown permission strings are rejected. Role changes still come only from the six fixed roles — overrides are the per-person layer on top. `assignments:manage`, `clients:read`, `clients:list-deidentified` and `records:manage-others` are rated *sensitive* in the catalog, as `clients:all` and `export:identified` are.

**Caseload scoping.** Whoever may open client records sees only the clients assigned to them unless they hold `clients:all` (`auth.caseloadRestricted`): denying `clients:all` puts a person back on their caseload in every place it is asked — client lists, records and search, exports, sync pull, the dashboard, reports. Holding `clients:list-deidentified` is no exemption (up to 1.15.3 it was, so a navigator granted it saw every client); the only account not held to a caseload without `clients:all` is a de-identified one, which cannot open any record and lists clients by code only. Putting someone on a care team (`POST /api/clients/:id/assignments`, and by sync) needs a client the actor can reach or `clients:all`, so `assignments:manage` is not a way around a deny of `clients:all` (M1). A de-identified role's client search (`GET /api/clients?q=`) matches an exact client code and nothing else: a name, date of birth or phone number finds nobody, in the same shape as no match, so it cannot ask whether a named person is a client (H2); every search is audited by the field it looked in (`searched`: `name`, `dob`, `phone`, `client_code`), never by what was typed.

## Account lifecycle

* Creation by an administrator, or a self-service *request* on the sign-in page that an administrator must approve and assign a role to (`POST /api/auth/signup`, can be switched off).
* Deactivation revokes sessions and queues a remote wipe of the person's local-mode devices (`server/devices.js`), and removes the person's passkeys (as SCIM deactivation and deprovisioning by absence do); an administrator can also revoke a person's passkeys on their own (Users → Edit; `DELETE /api/users/:id/passkeys`, audited `user.passkeys.revoked`).
* **Deprovisioning by absence.** Settings → Security policy → *Disable single sign-on accounts not seen for (days)* (`sso_deprovision_days`, 0 = off). Once a day an active account linked to the identity provider (an OIDC subject or a SCIM `externalId`) that the provider has not vouched for in that many days — no SSO sign-in and no SCIM update leaving it active (`users.idp_seen_at`; before that, its last sign-in or creation) — is disabled, its sessions revoked and its devices revoked with a wipe on their next sync, audited as `user.deprovisioned`. Emergency accounts are never touched. The report (who is due, who is due within 7 days, who was disabled in the last 90 days) is on Security status and at `GET /api/admin/security/deprovisioning`; *run now* is `POST /api/admin/security/deprovisioning/run` (users:manage) (`server/deprovision.js`).
* **Accounts without two-step verification** — role, whether it is required, deadline, overdue, SSO-linked, last sign-in — are listed on Settings → Security status and at `GET /api/admin/security/mfa-report` (users:manage, audited).
* Access reviews: the Users & permissions tab lists every account with role, MFA and last sign-in; a periodic review is a county procedure (see [SOC2-READINESS.md](SOC2-READINESS.md), CC6.2/6.3).

## Directory integration

**SCIM 2.0** (RFC 7643/7644) user provisioning, just enough for Entra ID and Okta: `GET /scim/v2/Users` (with `filter=userName eq "…"`, `externalId eq "…"` or `id eq "…"`, and `startIndex`/`count`), `POST /scim/v2/Users`, `GET`, `PUT`, `PATCH` (Entra's `"op":"Replace","path":"active","value":"False"` and Okta's value objects) and `DELETE /scim/v2/Users/{id}`, and `GET /scim/v2/ServiceProviderConfig`. Errors are SCIM error objects; responses are `application/scim+json`.

* **Set-up.** Security status → *Provisioning (SCIM)* → *Create a SCIM token* (users:manage; shown once, stored hashed, revocable, `last_used_at` recorded). In Entra ID: Enterprise application → Provisioning → Automatic, Tenant URL `https://<suds-host>/scim/v2`, Secret token = the token. In Okta: the app's Provisioning → SCIM 2.0, base URL the same, authentication *HTTP Header* (Bearer). The default attribute mappings work (`userName`, `displayName`/`name`, `emails`, `active`, `externalId`).
* **Roles.** SUDS keeps no Groups resource: group membership arrives as the user's `roles` or `groups` values (map *appRoleAssignments* or group names to `roles` in Entra; an Okta group-push attribute) and is mapped through `scim_group_roles` (`SUD Navigators=navigator; SUD Supervisors=supervisor`). Several mapped groups: the most privileged role wins. No mapped group: `scim_default_role` (readonly unless set). readonly is kept as the default deliberately: it can identify nobody (it holds neither `clients:read` nor `export:read`, which the de-identified-roles sweep above enforces), so an unmapped county employee lands on aggregate reports, the resource directory and the form library, and gets a real role only when someone maps their group. If even that is too much for your county, deactivate unmapped people at the identity provider instead of provisioning them. Role changes are audited with from/to.
* **Deactivation.** `active=false` (PATCH or PUT) or `DELETE` disables the account, revokes its sessions at once and revokes its local-mode devices with a wipe on their next sync (`scim.user.deactivate`). Accounts are never deleted: the audit trail refers to them. `active=true` reactivates.
* **Limits.** A provisioned account has no password (it signs in through OIDC, which links it on first sign-in). Emergency (break-glass) accounts cannot be changed or deactivated by SCIM (403, `mutability`). No bulk, no sort, no ETags, no Groups endpoint. Every create, update and deactivation is audited under the token's name (`scim:<name>`), and refused calls as `scim.denied`.

Without SCIM, disabling a person at the IdP stops new sign-ins immediately when SSO is required; *deprovisioning by absence* (above) then disables the SUDS account after the configured number of days, or an administrator deactivates it at once.

**Why not SAML.** SUDS supports OIDC, which Entra ID, Okta, Ping, Keycloak and ADFS (2016 and later) all offer, so a county identity provider can always be connected. SAML 2.0 would need XML canonicalisation and XML-DSig signature verification; there is no implementation of either in Node's standard library, and SUDS has no runtime dependencies by design (a hand-written XML-DSig verifier is a well-known source of signature-wrapping vulnerabilities). A county on SAML only can put an OIDC bridge in front (Entra ID, Okta and Keycloak all federate SAML to OIDC).
