# HIPAA, 42 CFR Part 2 and security controls

SUDS is designed to help a covered entity meet the HIPAA Security Rule (45 CFR §164.308–.316), the Privacy Rule's individual-rights and de-identification provisions, and the confidentiality requirements for SUD records under 42 CFR Part 2. Software alone does not make a program compliant: policies, training, risk analysis, BAAs and physical safeguards are the program's responsibility. This document maps the technical safeguards SUDS provides to the rule, and lists what remains for the organization.

## Technical safeguards implemented

| Requirement | Implementation |
| --- | --- |
| **Access control — unique user ID** (§164.312(a)(2)(i)) | Every user has an individual account; shared accounts are not supported. API keys are separate, write-only, and named. |
| **Access control — emergency access** (§164.312(a)(2)(ii)) | Administrators may open a clinical note only by supplying a break-glass reason of at least 15 characters. Each use is written to the audit log (`note.view.breakglass`, `note.list.breakglass`) **and** queued in Supervision → Break-glass access, where a supervisor or privacy officer must acknowledge it (nobody can acknowledge their own). The count of unreviewed accesses appears on the supervisor's home page. |
| **Automatic logoff** (§164.312(a)(2)(iii)) | Server-side idle timeout (default 15 min, capped at 60, editable in Settings) and absolute session limit (12 h); the browser warns one minute before sign-out. Sessions are revoked on password change. |
| **Encryption at rest** (§164.312(a)(2)(iv)) | All direct identifiers and free-text PHI are encrypted with AES-256-GCM using a key held outside the database: names, DOB, phone, email, address, Medicaid ID, emergency contact, goals, safety flags, call summaries **and purposes**, visit summaries, note titles and content, structured note sections, addenda, **task titles**, referral **outcomes, barriers and notes**, overdose **substances** and notes, consent and disclosure recipients, purposes, scope and **justifications**, break-glass reasons, patient-request notes, episode presenting problems and discharge summaries, completed county forms and their attachments, imported text and titles, MFA secrets. Search on encrypted fields uses keyed HMAC blind indexes so ciphertext is never scanned. The database should additionally sit on an encrypted volume. |
| **Encryption in transit** (§164.312(e)) | Native TLS 1.2+ support (self-signed certificate generated by the setup wizard, or a supplied certificate) or a TLS-terminating proxy; HSTS; `Secure`, `HttpOnly`, `SameSite=Strict` session cookies. Network access from other devices cannot be enabled without HTTPS. |
| **Audit controls** (§164.312(b)) | Every authentication event, PHI read (client view, note view, list, timeline, export, accounting of disclosures), write, permission denial, configuration change and API-key use is recorded with user, IP, entity, client and details. Each entry carries a keyed hash chained to the previous entry. Once a day (and after every retention purge) the server **seals the head of the chain**: the newest entry's id and hash and the row count are HMAC'd with the index key, stored in settings, and written to the log file at info level. Verification (Administration → Audit log, and the daily scheduled check) walks the chain **and** compares it with the sealed head, so deleting the newest entries — which leaves a chain that still verifies — is reported as `truncated`. The daily check is incremental: it resumes from the last entry it verified (whose id and hash are sealed with the index key, so the marker cannot be moved by editing the database) and walks the whole chain once a week; the Verify button always walks the whole chain. Both read 5,000 entries at a time and let other requests run in between, so a million-row log no longer freezes the server while it is checked. Because someone who holds both the database and the index key could still rebuild the whole chain, the head is also **anchored outside the database** every 6 hours and at every backup (`server/audit-anchor.js`): a write-once file per anchor, sealed with the index key and naming the anchor before it, in `AUDIT_ANCHOR_DIR` (a WORM share in a proper deployment) and optionally a syslog collector; verification compares the chain with every anchor, so a rewritten chain is reported. An auditor can take the chain away as NDJSON with a signed manifest (`GET /api/admin/audit/export`) and check it offline (`npm run verify-audit-export`). Retention defaults to 7 years. |
| **Integrity** (§164.312(c)) | Signed notes are locked; a signature hash over the encrypted content is stored and can be re-verified. Only the note's author may sign it; a supervisor **countersigns**, which is recorded separately so the record always shows who provided the service and who approved it, each with its own verifiable hash. A device can never assert a countersignature. Corrections are addenda, never edits. Consents, disclosures and addenda are **insert-only through sync**: a device may add to the legal record and may revoke a consent, but a push that would alter or resurrect one is refused as `immutable`. Records are soft-deleted with a required reason. AES-GCM authentication tags detect ciphertext tampering. |
| **Person or entity authentication** (§164.312(d)) | scrypt-hashed passwords (N=2^15, computed off the request thread), 12-character complexity policy, forced change of temporary passwords, lockout after 5 failures (15 min), login rate limiting, TOTP multi-factor authentication (RFC 6238), timing-safe comparisons. Multi-factor is **required of every role by default** (`MFA_REQUIRED_ROLES`) and enforced: after a grace period (14 days by default, settable to 0) an account can reach nothing but the enrolment screens until it is set up. |
| **Minimum necessary** (§164.502(b)) | Role-based permissions; navigators and clinicians see only clients on their caseload; finance and readonly see de-identified client codes only and hold neither `clients:read` nor (for readonly) `export:read`; clinical notes are visible only to clinical roles and supervisors. Exports require `export:read` (every role but readonly; a caseload-scoped role exports only its own caseload) and are de-identified unless the user holds the audited `export:identified` permission (supervisor, admin). The same limits apply to records a device uploads: every synchronised table carries the permission its API routes require, and caseload scoping is applied to pushed rows as well as pulled ones. |
| **De-identification** (§164.514(b)(2), Safe Harbor) | A de-identified export carries none of the eighteen identifiers: names, contact details and free text are redacted; every date is reduced to year-month; ZIP codes are cut to their first three digits; the city column is omitted; date of birth becomes an age band (18-24 … 65-89, `90+`). A de-identified dataset carries only an explicit allow-list of columns (`DEID_COLUMNS` in `server/exports.js`): free text, names, document and receipt references, vendors and locations are not on it. Files are labelled "De-identified (HIPAA Safe Harbor)" in the filename, the `X-SUDS-Export` response header and, for Excel, an *About* sheet. Text cells that a spreadsheet would read as formulas are neutralised. The funder report suppresses any breakdown row counting fewer than 11 people (`<11`) while keeping totals exact. |
| **Accounting of disclosures** (§164.528) | An identified export is itself a disclosure: it must name its recipient and purpose, and one accounting row (basis `export`) is written for every client it contains — one per client per file, so a workbook of a dozen sheets records one disclosure per client, and the workbook's own accounting sheet leaves those rows out. `GET /api/clients/:id/disclosures/accounting` (audited) and the **Print accounting** button on the Consents tab produce the accounting a client is entitled to. |
| **Individual rights** (§164.522, .524, .526, .528) | Requests for access, amendment, restriction or an accounting are recorded on the client's **Requests** tab with the date received; each carries a 30-day due date, is flagged when overdue, and is closed as fulfilled or denied with a note (encrypted). |
| **Retention and disposal** (§164.316(b)(2), §164.310(d)(2)) | Discharged client records (every episode closed), and records left inactive, are hard-deleted from every table by a daily job once their **last activity** is older than the retention period — `client_retention_years`, default 7, never below 6. Last activity is the latest date anywhere on the record: intake, discharge, episode opened or closed, and every visit, call, note, addendum, referral, to-do, consent, disclosure, form, overdose event, patient request, time entry or expenditure linked to it — so outreach logged years after a discharge keeps the record for another full period. Active and waitlisted records are never purged. Devices receive tombstones. An administrator can place a record on **legal hold**, which exempts it from the purge and blocks deletion until the hold is cleared (both audited). The purge is audited by client code only. |
| **Transmission of application security** | Content-Security-Policy (self only, no inline scripts), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on every response, CSRF protection via a required custom header on state-changing requests, JSON body limits, request timeouts, no third-party scripts or CDNs. The only outbound connections are ones an administrator configures: the optional Microsoft Graph (OneNote) connector, single sign-on discovery and key fetches from the configured identity provider, the optional release check (`UPDATE_FEED_URL`, only when clicked), and pictures for resource-directory entries loaded from a starter region file. The browser's own connect-src policy is `'self' https:` so those can work; no third-party script ever loads. |
| **Supply chain** | Zero third-party runtime packages; only Node.js built-ins. |

## 42 CFR Part 2

The rule-by-rule matrix against the **2024 final rule** (compliance date 16 February 2026), with file and route references and what the programme must supply itself, is [compliance/PART2.md](compliance/PART2.md). In short:

* **Part 2 programme setting** (`part2_program`, on by default; Privacy & Part 2 → Overview). While on, the client header carries the **42 CFR Part 2** label, a general release (ROI) is not accepted as consent, and everything that leaves the programme carries the §2.32 notice. Notes default to `part2_protected` and are labelled on screen and on paper.
* **Consents** capture every §2.31 element and the server refuses a Part 2 consent that lacks any of them: who may disclose, recipient (a name or a class), purpose, the information covered (scope), the right to revoke and how, an expiration (a date **or** an event), who signed (the patient, or a named parent, guardian or representative — §2.14/§2.15), evidence it was signed (a document reference, a witness, or "signed on paper"), the redisclosure statement, and the consequences of refusing to sign. Four Part 2 types: a named disclosure, the 2024 rule's **single consent for treatment, payment and health care operations**, a consent for **SUD counseling notes** only (§2.31(b)), and a consent for use in a **legal proceeding** only (§2.31(d)). Each consent prints as a PDF with every element. Consents recorded before the 2024 element list are marked *Pre-2024 form*.
* **Every disclosure goes through `server/disclosure.js`**: referrals (on creation, update and outcome), manual disclosures, and identified exports. It is refused without a live consent of the right type or another lawful basis; a consent cannot be stretched beyond its type (a TPO consent never covers counseling notes or a proceeding); a **court order** basis needs a recorded subpart E order for that client that states the required findings and met the notice requirement, is in force and not vacated; information **for use in a proceeding against the patient** needs such an order or a proceedings-only consent (§2.12(d)); **SUD counseling notes** need their own consent or an order that covers them; and a client's **agreed restriction** (§2.26) must be confirmed as checked. A referral that shares nothing — left pending, with no warm handoff — needs none.
* **Lawful bases other than consent** (§2.51 medical emergency, subpart E court order, qualified service organisation, audit/evaluation, research, crime on premises, child-abuse reporting) can be recorded by any role that records disclosures. A **medical emergency** must carry a written justification (at least 20 characters). **"Other"** is a supervisor/administrator override (`disclosures:override`) and must also be justified. Justifications are stored encrypted with the disclosure and appear in the accounting.
* **Revoking a consent** flags every open referral that relied on it. Revocation is the only change a synchronising device may make to a consent.
* **Accounting of disclosures** (§2.25 / HIPAA §164.528): each disclosure records recipient, purpose, information disclosed, method, legal basis, justification where required, the consent or court order relied on, whether it was for a legal proceeding or included counseling notes, and which §2.32 notice version went with it. Printable for the client from the Consents tab.
* **Identified exports** must name the recipient and purpose and state a lawful basis (`consent` — every client in the file needs a live Part 2 consent — `audit_evaluation`, `research`, `qsoa` or `internal`); a proceeding is never a bulk export. One accounting row per client; the file carries the §2.32 notice (Excel: the About sheet; CSV: the last row). An export naming more clients than the threshold opens a draft incident. De-identified exports follow Safe Harbor and are not Part 2 records.
  * The **county EHR hand-off** is an identified disclosure too. It keeps its own basis choice — each client's consent (clients without one are left out and listed), a QSOA, or a justified supervisor/administrator "other" — with the same consent types as a consent-based export (the single TPO consent qualifies; a general release only outside a Part 2 programme), the same agreed-restriction confirmation, the §2.32 notice in the file, and the mass-export incident.
  * The **CalOMS Tx submission** is required by law: it is recorded under the fixed `state_reporting` basis (no basis to choose, no consent checked, not stoppable by an agreed restriction) when the submission file is produced, against that file's id and SHA-256, with the §2.32 notice in its README and the mass-export incident (on producing it and on each download). The preview carries no names or dates of birth and is not accounted. Every one of these rows records the notice version, `legal_proceeding = 0` and `counseling_notes = 0`.
* **FHIR API** (docs/integration/FHIR.md): every FHIR answer that identifies a client is a disclosure to the organisation the FHIR client was registered for, made under the same rules as `requireBasis`. It is made only for clients with an active, unexpired, unrevoked consent that can authorise a disclosure here — a Part 2 consent naming that organisation for the purpose of use, or the single TPO consent naming it (alone or within a class); a general release only when `part2_program` is off — and no agreed restriction; others are omitted (and never confirmed to exist). SUD counseling notes are never listed, and note text is never sent. Each response carries the `R` / `42CFRPart2` / `NORDSLCD` security labels and the 2024 §2.32 notice, and one accounting row is written per client per request with the notice version. A bulk export is checked and accounted when each file is downloaded, not when it is built: a file naming a client whose consent has lapsed since the build is not released. FHIR clients authenticate at the token endpoint only (SMART Backend Services `private_key_jwt`, or a client secret the administrator may switch off); the secret is never itself a bearer token.
* **§2.32 notice** in the 2024 wording (`PART2_REDISCLOSURE_NOTICE` in `server/constants.js`): shown to the worker with every disclosure made under consent, and printed on exports, completed-form PDFs, consent PDFs, the accounting and printed notes.
* **§2.22 patient notice**: an administrator-editable, versioned notice of privacy practices (a built-in starting text covers the 2024 elements); each time a client is given it is recorded (date, method, by whom, version, acknowledgement). The Overview, Home and Privacy & Part 2 → Notice not given show who has not had it.
* **§2.4 complaints**: a complaint log (supervisors and administrators) with encrypted summary and resolution, whether the complainant was told they may complain to HHS, and a no-retaliation check; never deleted.
* **Breach notification** (§2.16 as amended, applying 45 CFR §§164.400–414): an incident register with the four-factor risk assessment, the determination and its reason, and computed deadlines — individuals within 60 days of discovery, HHS at once for 500 or more (otherwise the annual log), media for more than 500 in one state. Home warns within 14 days and when late. A failed audit-chain check, a break-glass access flagged at review, and a very large identified export open a draft incident automatically.
* Consent and court-order text, disclosure recipients and content, justifications, notice notes, complaint summaries and incident narratives are stored encrypted like any other PHI — who a client's records may be shared with is itself sensitive.

## Browser local mode (the offline copy) and sync

* The web application on the office server is the system of record (docs/PLATFORM.md). The native phone apps were removed in 1.9.3; what follows describes the browser's local mode, which is **off by default** from 1.9.3 and which a county turns on deliberately — the setup wizard's offline-copy question, or `LOCAL_MODE_ENABLED=true` — only for a documented field-work need.
* A local-mode browser stores its own encrypted database in that browser profile (AES-256-GCM, same scheme as the server, in IndexedDB). A plain browser has no protected key store, so the keys are generated on first run and kept in the same profile's `localStorage`, beside the data: anyone who can use the profile can read what is in it. Local mode therefore belongs only on county-managed devices with a device passcode, disk encryption and MDM remote wipe, and only for the people and devices the county has approved.
* Sync transmits records over HTTPS to the office server, authenticated with the user's office credentials (and MFA where enabled); PHI is decrypted for transport and re-encrypted with the receiver's own key. Credentials are not stored on the device; each sync uses a short-lived session.
* The server enforces minimum necessary on sync: only the user's caseload is downloaded; clinical notes, ASAM assessments and outcome measures (screening answers) only for clinical roles; MFA secrets and other users' credentials are never sent. Uploads are attributed to the syncing user, cannot change approvals or signed notes, cannot alter or delete consents, disclosures or addenda (a consent may only be revoked), cannot delete clients or notes, and are rejected outside the caseload. Every sync is audited on the server, including the device's own audit entries. Break-glass events are reviewed on the office server and are not synchronised.
* The office server is authoritative: permanent sync rejections are final and the device stops resending them; a purged or merged record cannot be resurrected from a device; each office account has its own sync cursor on a device. Every local-mode browser that syncs is listed under Settings → Synced devices, where an administrator can revoke or wipe it; deactivating an account or resetting its password queues a wipe for its devices. With local mode off (the default; `LOCAL_MODE_ENABLED=false` or the wizard's *No*), the server serves an explanation instead of the kernel.

## SUDS on this device (the web app on GitHub Pages)

* From 1.9.5 the GitHub Pages build is a production way to run SUDS for people without an office server (`WEB_APP.md`). Its records are stored in one browser on one device, encrypted exactly as local mode stores them (AES-256-GCM in IndexedDB, keys in the same profile's `localStorage`), and never leave the device: there is no sync, and the app sends no record data anywhere.
* **Access control on the device.** Accounts are created on the device with Sign up; the first one manages the device and can turn further sign-ups off. Later accounts are navigator accounts, and once there is more than one account every navigator and clinician sees only their own caseload. Passwords follow the same policy as the office server; every sign-up, sign-in, backup and restore is in the device's hash-chained audit log.
* **Availability and integrity (§164.308(a)(7)).** The records exist only on the device, so the contingency plan is the device backup: an AES-256-GCM file keyed by PBKDF2-SHA256 (600,000 iterations) from a passphrase the person chooses, holding the database and its keys, restorable only with that passphrase, refused if altered. The first-run Sign up states where records are kept and requires the person to confirm it; Home reminds the device's manager after 7 days without a backup; the app asks the browser for persistent storage and shows whether it was granted.
* **Hosting.** GitHub serves the app's code only. No PHI reaches GitHub, so no Business Associate Agreement applies to the hosting, but a county using the on-device app should record in its risk register that the code is served from GitHub (or self-host the build, `WEB_APP.md`).

## Risk register notes

Residual risks a county should carry in its own risk register (§164.308(a)(1)). None is a defect; each is a consequence of a design choice, stated so it is weighed rather than discovered.

| Risk | What it means | Mitigation in place / what the county does |
| --- | --- | --- |
| **Blind-index equality and frequency leakage** | The `_idx` columns (`last_name_idx`, `full_name_idx`, `first_name_idx`, `preferred_name_idx`, `name_prefix_idx`, `first_name_prefix_idx`, `name_phonetic_idx` — a Soundex code —, `dob_idx`, `phone_idx`) are deterministic HMACs. Anyone holding the database file *without* the keys cannot read a name, but can see which rows share a value: which clients have the same surname, date of birth or phone number, how common each value is, and (from the three-letter prefix and Soundex columns) coarse groupings of similar names. Frequency analysis against a public name list can suggest likely surnames for the commonest values. | The keys never sit beside the database in a proper deployment (secrets manager or `data/keys.json` excluded from IT backups); the database is on an encrypted disk; backups are themselves AES-256-GCM encrypted, so a stolen backup leaks nothing, indexes included. Treat a copy of `suds.db` without its keys as a limited disclosure of *relationships*, not as harmless. |
| **One key, two uses: index key and audit chain** | `SUDS_INDEX_KEY` keys both the blind indexes and the HMAC that chains and seals the audit log (`server/audit.js`). Someone who has the index key (for example to run a search-side tool) could also forge a consistent audit chain; rotating one rotates the other (`npm run rotate-index-key` re-signs the chain). | Documented, not yet separated: deriving a distinct audit key (HKDF of the index key with its own label) needs a one-time re-sign of every existing chain and a matching change in the browser kernel, so it is scheduled as its own change rather than folded into another. Until then, give the index key the same custody as the encryption key, and keep the sealed-head checkpoint line in the collected log (it lives outside the database). |
| **Single instance, single SQLite file** | One process and one database file (DEPLOYMENT.md, "Single instance only"). No high availability: a host failure is an outage until the host or a restore is back. | Scheduled, off-host, encrypted backups; a recovery drill (`npm run dr-drill`, or Settings → System & backups) that restores the newest backup into a throwaway copy and records the measured RTO and RPO; a warm standby procedure (DEPLOYMENT.md, "County hosting options"); a bigger host rather than replicas. |
| **Local-mode keys beside the data** | In local mode the offline copy's encryption and index keys are generated in the browser and kept in that profile's `localStorage`, next to the encrypted IndexedDB database. Anyone who can use the browser profile (an unlocked device, a synced profile, malware) can read the caseload on it. | Local mode is off by default from 1.9.3. Where it is on: county-managed devices only, with passcode, disk encryption and MDM remote wipe; revoke/wipe from Settings → Synced devices; deactivation queues a wipe (PLATFORM.md). |
| **On-device app: records in one browser** | SUDS on this device (GitHub Pages) keeps its records only in the browser that holds them, with the keys beside them. Clearing the browser's site data, a browser evicting storage, or a lost or broken device loses every record not in a backup; anyone who can use the browser profile can read them. The code is served from GitHub, with which there is no BAA (none is needed for code that never receives PHI), and a compromise of the repository or the Pages site could serve altered code. | First-run confirmation of where records are kept; encrypted device backups with a 7-day reminder; persistent-storage request and status; caseload scoping between accounts on one device. The county: decides whether the on-device app may hold client information at all, requires device passcode/disk encryption/MDM, sets a backup routine and where backup files are kept, records the GitHub hosting (or self-hosts the build), and prefers an office server where records must be shared or retained centrally. |
| **Experimental runtime module** | `node:sqlite` is experimental in Node 22 and 24. | CI runs the suite on Node 24 in advance; migration plan in DEPLOYMENT.md ("Node.js support and the move to 24"). |

## Organizational responsibilities (not provided by software)

1. **Risk analysis and management** (§164.308(a)(1)) — document this deployment in your risk register, starting from *Risk register notes* above; the adoption plan (pilot, release cadence, drills, independent review) is [ADOPTION.md](ADOPTION.md).
2. **Workforce training and sanctions** — users must understand break-glass, minimum necessary and Part 2 rules.
3. **Business Associate Agreements** — with any hosting provider, and with Pocket AI or Microsoft if PHI is recorded or stored in their services before import.
4. **Device and media controls** — encrypted laptops/phones used with Pocket AI or approved for local mode; retire any remaining phone-app installs (the apps were removed in 1.9.3; docs/PLATFORM.md); secure disposal of backups.
5. **Contingency plan** — run the encrypted backups (docs/DEPLOYMENT.md) and test restores.
6. **Audit review** — acknowledge break-glass events as they arrive (Supervision → Break-glass access) and review access denials and exports at least monthly. Confirm the audit verification runs and the sealed-head checkpoint line appears in the collected log.
7. **Patient requests** — answer access, amendment, restriction and accounting requests within the 30 days the Requests tab tracks; a denial must be given to the client in writing.
8. **Retention policy** — set `client_retention_years` to your state's rule if it is longer than 7, and place legal holds when counsel asks.
9. **Breach notification** — record every possible breach in the incident register (Privacy & Part 2 → Incidents & breaches) on the day it is discovered; SUDS computes the 60-day, HHS and media deadlines and will not close a breach until the notices are recorded, but the risk assessment, the determination, the notices themselves and any substitute notice are the programme's, with counsel.
10. **Physical safeguards** — server room / cloud region controls, workstation placement.
11. **42 CFR Part 2 policies** — counsel-approved consent, revocation and patient-notice wording; a complaint procedure (§2.4) with no retaliation; security and breach policies (§2.16); staff training on the 2024 changes (TPO consent, counseling notes, the bar on use in proceedings, court orders). See [compliance/PART2.md](compliance/PART2.md) for the full list.

## Key management

* `SUDS_ENCRYPTION_KEY` and `SUDS_INDEX_KEY` are 256-bit keys supplied by the environment, or generated into `data/keys.json` (mode 0600) on first run for installations without an IT-managed secret store. In that case the administrator must download the key backup (Administration → System) and store it separately from database backups. Rotate with `NEW_ENCRYPTION_KEY=<hex> npm run rotate-key` during a maintenance window (server stopped, backup taken). Never commit keys.
* Backups are encrypted with a key derived from the encryption key; store keys and backups separately.

## Resource pictures
Pictures on treatment center profiles are meant to show buildings, entrances and rooms. They are not PHI and are stored unencrypted alongside the resource record so they can be shown quickly and synced to local-mode devices. Staff are reminded in the app never to upload pictures of clients; if one is uploaded by mistake, remove it from the profile (audit-logged) and note the incident per your policy.

## County forms
Filled-out forms and attached signed copies are PHI: their values and files are stored encrypted (AES-256-GCM) with the client record, every view, print and attachment is audit-logged, and access follows the same caseload rules as notes. Blank templates in the form library are not PHI and are shared with every device. Printed PDFs carry a Part 2 / HIPAA handling notice; treat paper copies per your program's policy.
