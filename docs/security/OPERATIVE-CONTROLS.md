# Operative controls

The release and repository controls that buyers are told about, and that work only if someone does something at each
release or keeps a setting on. For each one, this page gives its **state today** and **how it is checked**. It is short
on purpose. The evaluation of 1.25.5 (J11) found two of these controls off, unnoticed, under 25,000-word process
documents: the release checksum's second channel (J1) and private vulnerability reporting (J2). The evaluation of
1.25.6 (K1) found that this page had no row for the repository protections themselves, and that the records described
release approvals that cannot have happened: those rows are below, each **off** today.

**State as of 2026-10-12, newest release tag `v1.25.6`.** `scripts/release-state.js` reads the rows whose first cell
starts with an id it knows: `checksum-main`, `checksum-release` and `signed-tag`, and, online, `main-ruleset`,
`release-reviewer` and `immutable-releases`, which it reads from GitHub's public API without a token (the rules on
`main`, the newest tag's release run and its approvals, the newest Release; "not checked" when the API is
rate-limited). It fails when a row's state (the bold words that start its State cell) is not the true one, in either
direction. CI runs it on every push (the advisory `release-state` job). Change a row when the state changes. The other
rows are checked where their last column says. Every owner action below is a step of
[../RELEASE.md](../RELEASE.md), *Owner: repository settings*: repository settings only the owner can change.
