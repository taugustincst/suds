# SUDS REST API

All endpoints are under `/api`. Authentication is a session cookie set by `POST /api/auth/login` (browser) or an `Authorization: Bearer <session token>` header; state-changing requests from a cookie session must include `X-Requested-With: suds`. Intake endpoints use an API key. Responses are JSON; errors are `{ error, fields? }`. List endpoints accept `limit`, `offset`, `client_id`, `from`, `to`, `mine=1` and `user_id` where applicable. Every PHI access is audited.

Permissions per role are defined in `server/auth.js` (`PERMS`). Generated by `scripts/gen-api-docs.js`.

## Intake payload (Pocket AI)

```
POST /api/intake/notes
Authorization: Bearer suds_<key>
Content-Type: application/json

{ "title": "...", "transcript": "...", "summary": "...", "action_items": ["..."], "created_at": "2026-09-10T15:04:00Z", "tags": ["field"] }
```

A JSON array or `{ "notes": [...] }` is also accepted. Response: `202 { import_id, staged }`.

## FHIR R4 API

`/fhir/R4` is a read-only FHIR R4 API for the county EHR or an HIE (Patient, EpisodeOfCare, Encounter, Consent, ServiceRequest, Task, Observation, DocumentReference, Organization, Location, HealthcareService, and Bulk Data `$export`). It answers in `application/fhir+json`, authenticates FHIR clients (created under Settings → FHIR clients, `/api/admin/fhir-clients`) with a 15-minute bearer token from `POST /fhir/R4/auth/token` (OAuth2 client credentials; the client signs a JWT with its registered key, SMART Backend Services `private_key_jwt`, or sends its secret; the secret is never itself a bearer token), and returns a client's records only under a live 42 CFR Part 2 consent naming the FHIR client's organisation, recording each disclosure. Endpoints, mappings, scopes and examples: [docs/integration/FHIR.md](integration/FHIR.md).

## Break-glass

Administrators may read a clinical note by sending `X-Break-Glass-Reason: <reason>` with `GET /api/notes/:id`; the access and reason are written to the audit log.

## Retries and concurrent edits

- **Idempotency-Key** (POST): send a key (1-255 printable characters) and a repeat of the same request by the same user within 24 hours returns the first answer (with `Idempotent-Replayed: true`) instead of running again. The same key with a different body is refused with 422. Only successful answers are remembered. Not applied to sign-in, sync, setup or account routes.
- **if_updated_at** (PUT body): the `updated_at` of the record as you loaded it. If the record has changed since, the save is refused with `409 { error, stale: true, updated_at }` and nothing is written. Omit it to save unconditionally. Successful PUTs return the new `updated_at`.
- **Client-record history** (1.17.0): `GET /api/clients/:id/history` returns `{ revisions, may_revert }`, newest first, each `{ id, at, by, via, reverts, reverted_by, changes: [{ field, label, before, after }] }`, for the client's care team and `records:manage-others` (anyone else 403, audited); on a device that syncs with an office 403 with `officeOnly: true`. `POST /api/clients/:id/history/:rev/revert` (the primary worker or `records:manage-others`; accepts `if_updated_at`) puts the change's fields back and answers `{ ok, updated_at, revision }`, or 409 with `changed_since` (field names) when a field has changed again since. `PUT /api/clients/:id` answers the new `revision`; a change notice's task carries `notice_revisions`.
- **Re-admission**: `POST /api/clients/check-duplicates` returns `readmit` (discharged records outside the caller's caseload that match on surname + date of birth or phone). `POST /api/clients/:id/readmit { first_name, last_name, dob, phone, reason }` assigns the caller, opens an episode and queues the event for supervisor review; the reason must be at least 8 characters.
- **A visit with its note**: `POST /api/interventions` accepts `note: { kind, format, title, content, structured, part2_protected }` (a client is required). The note is created as a draft linked to the visit, in the same transaction, under the notes permissions and rules; the response carries `note_id`. A refused note (403, or 400 with `fields.note_*`) saves nothing. `PUT` does not accept a note.
- **Time entries' source**: `GET /api/time` rows carry `source` (`visit`, `call` or `manual`); the list filters on `source=visit|call|manual` and, for `time:all`, `user_id`.
- **Approved time is locked** (1.15.3): `PUT` and `DELETE /api/time/:id` on an entry with status `approved` answer 409, for the worker and for `time:all` alike, and sync push refuses the same edit or deletion (`not permitted`, permanent). `POST /api/time/:id/approve` with `decision: "rejected"` and a `note` returns an approved entry to its worker (audited `time.rejected` with `reopened: true`); it can then be corrected and resubmitted.
- **County view** (released in 1.18.0; office server only, [COUNTY-VIEW.md](COUNTY-VIEW.md)): `GET /api/county-submission/file?from&to&county_code&county_name&funds=id,id` (`reports:funder`, `budget:read`, `export:read`; the period must have ended, the funds be settlement funds) answers the signed county submission file, JSON `{ format: "suds-county-submission", schema_version: 2, payload, signature: { algorithm: "Ed25519", key_fingerprint, value } }`, the payload carrying `recipient: { county_code, county_name }` and the chosen funds only, the signature over its canonical serialisation (keys sorted, no whitespace); `POST /api/county-submission/key` makes the key without a file and `POST /api/county-submission/key/new` retires it for a new one. `GET /api/county/code` (`county:view`) is the county's code. `POST /api/county/submissions { text }` (`county:manage`) imports one: `201 { status: "imported" | "superseded" | "older", message, submission }` (`older`: kept, but a file made later counts), `200 { status: "duplicate" }`, or `422` (`413` when over 256 KB) `{ error, reason }` with `reason` one of `malformed`, `format`, `schema`, `period`, `recipient`, `unknown_key`, `inactive`, `signature`, `retired_key`; refusals are throttled per person (`429`). `POST /api/county/submissions/:id/withdraw { reason }` and `/reinstate`; `POST /api/county/programmes/:id/keys { public_key, fingerprint | compared, old_compromised }` replaces a programme's key and `PUT /api/county/programmes/:id/keys/:keyId { compromised }` marks a replaced one. `GET /api/county/view?from&to` (`county:view`) returns `{ programmes, rows, whole, part, none, of, headline, inactive_left_out, caveats, caveat_summary, rule, publication_note }`, each row `{ group, key, label, money, by: { programme_id: value | null }, total }`; `&by=quarter` returns `{ quarters, rows }` with `by_quarter` per row. `GET /api/county/view/export?from&to&format=xlsx|csv|tidy`. **County-entered figures** (released in 1.20.0; [COUNTY-VIEW.md](COUNTY-VIEW.md) *County-entered figures*): `POST /api/county/programmes { name, notes?, not_on_suds: true }` registers a programme with no key; a name already registered (whatever the case or spacing) is refused on registering either kind and on renaming (`409 { reason: "duplicate_name", fields: { name } }`). `POST /api/county/programmes/:id/entries { from, to, source_ref, funds: [{ name, grant_number?, category, hiaa?, spend_own_category, spend_other_categories, spend_pending, <each outcome> }] }` (`county:manage`; figures as strict numbers) answers `201 { status: "entered" | "superseded" | "older", message, submission }`, `400 { error, reason: "invalid", fields }` (fields named `from`, `to`, `source_ref`, `funds.0.contacts`, …) or `409 { reason: "on_suds" | "inactive" }` (a programme that has joined SUDS gets no more entries: its entered figures can be withdrawn and reinstated, not corrected). `POST /api/county/programmes/:id/entries/import { text, source_ref, funds: [{ name, grant_number, category, hiaa }], preview? }` takes the tidy CSV (`program, period_from, period_to, fund, grant_number, measure_code, measure_label, value[, source[, source_label]]`), `preview` writing nothing; only the programme's own rows are read (another programme's are counted in `others: [{ name, rows }]` and said in `warnings`, never imported), a `source` of `signed` is warned about in `warnings`, and a file is refused with `422 { error, reason: "csv", errors: [{ row, column, message }] }`. Refused entries and imports are throttled per person (`429`), as refused files are. `GET /api/county/programmes/:id/entries/template?from&to` (`county:manage`) is the tidy CSV's header and a row per measure of each of the programme's funds, values empty; `GET /api/county/entries/:id` (`county:manage`) is an entry in the form's shape. Submissions carry `source` (`signed` or `county_entered`) and `entered_via`; `GET /api/county/submissions` rows carry `programme_on_suds`, and `source_ref` for `county:manage` only. A signed file always outranks entered figures: for one period it counts whatever either's `generated_at`, and in the combined view entered figures that overlap a signed file are in `left_out` with `why: "signed_covers"` (each left-out file has `why` and `reason`). The combined view's programmes carry `source` (`signed`, `county_entered`, `mixed` or null) and its rows `total_entered`, with `entered_programmes`, `entered_left_out` and `has_entered`; `&entered=include|exclude` on the view, its export and the read API's `/v1/combined` (anything else `400`) counts or leaves them out. The tidy CSV has `source` (`signed` or `county_entered`, as the read API says it) and `source_label`. The county connection's `/v1/status` counts only signed files as received, and each `received` item carries `source`.
- **County publication releases** (released in 1.21.0; office server only, [COUNTY-VIEW.md](COUNTY-VIEW.md) *Publication*): `POST /api/county/publications/prepare { from, to, entered?: "include" | "exclude", threshold? }` (`county:manage`) screens the combined figures of a period that has ended and answers `{ content, sha256, threshold, review_confirmation }` without recording anything; `content` is `{ format: "suds-county-publication", schema_version: 1, county, period, method, release_id, programmes: [{ name, coverage, source }], figures_entered_by_the_county: { counted, programmes, left_out }, rows: [{ section, group, key, label, money, value, screened?, suppressed? }], suppressed: [{ key, label, shown, reason, why }], withheld, notes }`, a screened `value` being a number, `"<T"`, `"suppressed"` or `"withheld"`. `POST /api/county/publications { from, to, entered?, threshold?, sha256, reviewed: true }` publishes it (`201`, the record) only when the figures still give that `sha256` (`409 { reason: "changed" }` otherwise) and the person confirmed the review (`428 { reason: "review_required" }`). Refusals: `400` (`period`, `threshold`), `409 { reason: "overlap" }` (a release already published, or withdrawn, overlaps the period), `422 { reason: "no_figures" | "refused" }` (nothing to publish, or the check could not protect it). `GET /api/county/publications` and `/:id` (`county:view`), `GET /api/county/publications/:id/export?format=csv|xlsx|json` (also `export:read`; the Excel has About, Figures and Notes sheets), `POST /api/county/publications/:id/withdraw { reason }` (`county:manage`: a withdrawal record of its own; nothing is changed or deleted). The read API's `GET /api/county-connect/v1/publications` (read token) lists every release as published, with `status` and `withdrawn_at`.
- **County connection** (released in 1.18.0; off by default; office server only, [COUNTY-VIEW.md](COUNTY-VIEW.md) *Connecting*). Machine routes, a bearer token and never a session, 404 while `county_connect_enabled` is off: `POST /api/county-connect/v1/submissions` (a connection token, `sudscc_…`; the body is the signed county submission file, at most 256 KB, read only for a live connection token) answers `201 { status: "imported" | "superseded" | "older", reason: null, message, period, receipt: { sha256, received_at } }`, `200 { status: "duplicate", … }`, or `422`/`413` `{ status: "refused", reason, message, receipt }` (`reason` the import's own, `recipient` and `retired_key` included, or `wrong_programme` when the file's key is another programme's than the token's; `message` the county view's words); `GET /api/county-connect/v1/status` (the same token) answers `{ county: { code, name }, programme, cadence, expected: [{ from, to, label, received, coverage }], outstanding, received: [{ from, to, sha256, received_at, generated_at, status }] }` (`code` the county's eight-character code a file must name; `label` as the Send to the county card names the period; counted by the combined view's rule, so a withdrawn, replaced or compromised-key file does not count); `GET /api/county-connect/v1/combined?from&to[&format=json|tidy-csv]` and `GET /api/county-connect/v1/programs` (a read token, `sudscr_…`) answer the combined view with `notes` (summed, not unduplicated; exact, internal, not for publication) and the programmes with their current key's fingerprint, their key history (fingerprints and dates) and the periods of their files that count. Wrong or missing tokens `401` (with `WWW-Authenticate: Bearer`), the wrong kind `403`, limits `429`. Signed in: `GET|PUT /api/county-connect/settings` (`county:view`; changing needs `county:manage` and `settings:manage`), `GET|POST /api/county-connect/tokens` and `POST /api/county-connect/tokens/:id/revoke` (`county:manage`; `POST` `{ scope: "county.submit", programme_id, expires_days? }` or `{ scope: "county.read", name, expires_days? }` answers the token once); on a programme's server `GET|PUT|DELETE /api/county-connect/connection` (`PUT`/`DELETE` `settings:manage`; the token is never returned), `POST /api/county-connect/connection/test`, and `POST /api/county-connect/send { from, to, funds?, county_code?, county_name? }` (`reports:funder`, `budget:read`, `export:read`; the file names the county's code from its status, and a `county_code` given must be it; `funds` default to those last chosen for that county, and none is refused) answering `{ status, reason, message, receipt, send }`.
- **Award amounts and reporting reminders** (released in 1.21.0; [COUNTY-VIEW.md](COUNTY-VIEW.md) *Award amounts* and *Reminders on the programme's side*). The county file is `schema_version: 2`: each fund carries `award: { amount, from, to } | null` (the fund's `total_amount` and `fiscal_year_start`/`fiscal_year_end`; null when no amount above 0 is recorded), signed with the rest; `GET /api/county-submission/file?…&schema_version=1` makes a version 1 file (no award) for a county on SUDS 1.20 or earlier, which refuses version 2. Built for 1.22.0, not yet released: without `schema_version` the file is version 2 only when the county is known to read it (the connected county's `/status` says so for that code, or the programme answered `county_suds=1.21+`), else version 1; `county_suds` (`1.21+`, `1.20-`, `unknown`; anything else `400`) is remembered per county code, the response carries `X-SUDS-County-File-Version`, the audit `version_source` (`asked`, `connection`, `answer`, `unknown`), and `GET /api/county-submission/options` each county's `county_suds`, `version` and `version_source`. The envelope's `schema_version` must equal the payload's. The county reads versions 1 and 2: the combined view adds rows of `group: "award"` (`award_amount`, `award_spent`, `award_spent_pct` with `percent: true`), each with `by_note: { programme_id: "award not in file" | "no award recorded" }` where a programme with figures has none and `total_over` (the programmes the total is over; the total is null when none), each programme `award: { status: "whole" | "partial" | "none" | "not_in_file", amount, spent, pct, … }` and `award_note`, and the view `award: { programmes_with, of, note }`; `&by=quarter` rows carry `by_quarter_over`. The tidy CSV (export and entry import) has the optional measure codes `award_amount`, `award_from`, `award_to` per fund (the dates in `value`; all three or none), as do the entry form's funds (`award_amount`, `award_from`, `award_to`) and the per-program template. The county connection's `/v1/status` adds `accepts_schema_versions` (a county that omits it reads version 1 only: `POST /api/county-connect/send` then makes version 1), `due_days` and each expected period's `due_by`; `PUT /api/county-connect/settings { due_days }` (1 to 180, default 30); `GET /api/county-connect/connection` adds `county_reads`, `county_older`, `county_older_note` and `send_version`. Reminders on a programme's server (`reports:funder`, `budget:read`): `GET /api/county-submission/reminders` answers `{ counties: [{ county_code, county_name, source: "county" | "programme", cadence, due_days, start, periods: [{ from, to, label, due_by, state: "received" | "sent" | "made" | "made_not_sent" | "due" | "overdue", done, made, sent }] }], reminders: [{ county_code, from, to, due_by, state, overdue, text }], connection }`; `PUT /api/county-submission/schedules/:code { county_name?, cadence, due_days?, start? }` (`cadence` `quarterly_calendar`, `quarterly_fiscal` or `monthly`; `400 { fields }`) and `DELETE /api/county-submission/schedules/:code` (`404` when there is none) answer the same, audited `county_submission.schedule.save`/`.remove`.
- **Fingerprint sign-in and signing (passkeys)** (released in 1.19.0; office server only, [FINGERPRINT.md](FINGERPRINT.md)). WebAuthn JSON with base64url strings. `GET /api/auth/passkeys/status` → `{ signin, signing, available, reason }`. Sign-in (no session, CSRF header required): `POST /api/auth/passkeys/login/options` → `{ purpose: "login" | "mfa", publicKey }`: discoverable passkeys only (`allowCredentials` empty; a `username` sent is ignored), at most 20 unanswered per address (`429`); with a session still owing its second step, the options finish it and list that account's passkeys. In production without `WEBAUTHN_RP_ID` every options route answers `503 { passkeyUnavailable: "config" }`, then `POST /api/auth/passkeys/login { credential }` sets the cookie (`401/403/423 { error, passkeyError }`: a reason code such as `uv`, `origin`, `rpid`, `signature`, `challenge_used`, `challenge_expired`, `counter`, `unknown passkey`). Enrolment: `POST /api/auth/passkeys/register/options { password, code? }` → `{ publicKey }` (creation options: platform authenticator, UV required, attestation none, ES256/EdDSA/RS256), then `POST /api/auth/passkeys/register { credential, name }` → `201 { passkey }`. `GET /api/auth/passkeys` (own list, no keys), `PUT /api/auth/passkeys/:id { name }`, `DELETE /api/auth/passkeys/:id { password }`. Signing and approvals: `POST /api/auth/passkeys/challenge { purpose, note_id | ids [+ decision] | id [+ status] }` with purpose `note.sign`, `note.cosign`, `note.cosign-batch`, `time.approve`, `expenditure.approve` or `keys.download` → `{ statement_hash, publicKey }`; the assertion goes as `passkey` in the body of the route it confirms (`POST /api/notes/:id/sign`, `/cosign`, `/api/notes/cosign-batch`, `/api/time/:id/approve`, `/api/time/approve-batch`, `/api/budget/expenditures/:id/approve`, `/api/admin/keys-backup`), which refuses one bound to other records or changed content (`403 { passkeyError: "another record" | "record changed" }`). Time and spending approval also accept `password` or `code`, and require a fingerprint or code when `sign_strong_required` is on (`403 { strongRequired: true }`). A password sent with a `code` is checked with it, and a wrong code refuses the request; a `passkey` sent with a password or code is refused (`400`). `GET /api/notes/:id/verify` adds `fingerprint: { verified, at, content_hash, reason }` (and `cosign_fingerprint`): the evidence checked against the passkey's enrolment record and the note's plaintext content hash now. `GET /api/auth/me` `user.passkey_mfa`: whether the account's passkeys count as two-step verification now. The authenticator allow-list's grace period (built for 1.22.0, not yet released): `PUT /api/admin/authenticator-allowlist` and its `/preview` take `grace_days` (0 to 90; 14 until set), the preview's `affected` gives each passkey's `stops_at` (null: at once), `only_factor_accounts`, `stops_now_count` and `grace_until`; `GET /api/auth/me` `user.passkey_grace` and `GET /api/auth/passkeys` `grace` (`{ until, passkeys, accepted_left, totp }` or null) and each passkey's `stops_at` and `stop_reason`. Administrators: `GET` and `DELETE /api/users/:id/passkeys`, `DELETE /api/users/:id/passkeys/:pid` (`users:manage`); `GET /api/admin/signature-evidence?record_type&record_id` (`audit:read`) returns the evidence, each row with its passkey's `enrolment` record (from the audit log), verifiable offline with `npm run verify-passkey-evidence` (`--audit <audit export>` reads the enrolment record from a verified audit export). Settings: `passkey_signin`, `passkey_signing`, `sign_strong_required`.
